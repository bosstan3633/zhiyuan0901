## 一、拆分的目的是什么

**一句话：设置页 2,899 行是全库第一大文件，拆分是为了让它能被安全地改动。**

这个目的必须分三层说，因为其中两层容易被误解：

### 第 1 层 · 直接收益：拆分不改任何界面

这一点经实测确认，不是承诺：拆分前后的 `git diff` 里，搬走的模板与样式**逐字**进入子组件，
宿主把一段 `<div>` 换成一个组件标签。**零像素意图变更。**

所以拆分**不改善体验、不改视觉、不动交互**。如果你期待的是"拆完设置页会变好用"，
那答案是不会 —— 拆的是代码结构，不是产品设计。

### 第 2 层 · 真实收益：降低"改设置页"的风险

设置页有 214 处判据直接读它的源码正文，横跨 16 个判据分片。这构成一个真实的维护成本：

| 现状（2,899 行单文件） | 拆分后的样子 |
|---|---|
| 想动一个子域，得先在 2,899 行里定位它 | 打开对应子组件即可 |
| 改错了，红的是**另外 15 个分片的判据**，看不出真因 | 红的判据指向本子域 |
| 交接时评审方要读懂整个文件才能审一个子域 | 只读那一个文件 |

本批已经验证了这套机制有效：拆出「一封信」子域后，宿主从 2,929 降到 2,899 行，
而 **214 处判据一条未改、全绿**。

### 第 3 层 · 代价（必须如实说）

拆分不是免费的，有三项真实成本：

1. **锚点迁移层**：必须先把设置页接进 `helpers.cjs` 的聚合读取机制，否则一动就是红海（本批已完成）
2. **每次拆完要跑全门禁 + 重跑代码索引**（census 实拍 6 分钟）
3. **拆错也能编译通过**：拆得太碎会让"一个设置页"的概念散在 17 个文件里，反而更难读

⇒ **判断标准**：只有当单个子域能独立讲清、且有独立改动理由时，才值得拆。
按当前代码看，`shortcuts`（快捷键）、`tags`（标签管理）、`ai`（AI 助手）这三块最独立，适合下一批；
而四张卡字段页共享同一套字段配置机制，适合合并成一批搬，不宜拆成四个。

## 三、审核方法

打开索引页 `index-linear.html`，16 张按导航组分区排列，左栏可对照真实分组。

审时请重点看三件事：

1. **左栏分组**是否符合你的使用直觉（当前：卡片与字段 / AI 认知协作者 / 数据与信任 / 系统信息）
2. **各子域的信息密度**是否有明显失衡的页（尤其 `changelog` 是超长时间线）
3. **已拆出的「一封信」** 与其他页视觉是否完全一致（这是拆分无副作用的直接证据）

若需要换主题核对（四主题 `linear/raycast/apple/notion`），可执行：

```bash
cd v2 && node scripts/shoot-settings-prototype.cjs --theme=raycast
```

## 四、实拍脚本的纪律备案

新脚本 `v2/scripts/shoot-settings-prototype.cjs` 照抄了 `theme-audit.cjs` 的既有做法，不是新发明：

- 用 `browser.cjs` 的四级回落定位 Chromium（脚本各自抄一份解析逻辑是 R4-Ea 治过的病）
- 扩展 host 从 `serviceWorkers()` 动态取
- 首次进入等初始化完成再注入，否则被 `createDefaultData` 覆盖
- 注入后强制整页重载一次（运行中的 store 持有旧引用，不重载读不到新偏好）
- **等子域面板真出现，不等固定时长**；且截图前核对 hash 仍是目标子域

16 张塌成 1 张（截图文件都还在，只有索引丢了）。已改为读既有记录做并集，并验证补拍后索引仍为 16 张。
