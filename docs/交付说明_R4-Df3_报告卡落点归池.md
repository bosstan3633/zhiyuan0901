# 交付说明 · R4-Df3 —— 报告卡落点归池：hubDeck 那枚巧合退役（未升版）

轮次 D 第八刀。起因不是计划，是 D-f2 收口时把手册里剩下的「资源台」按行号逐条读完——
其中 5 处是"这东西已退役"的说明句（该留），第 6 处（`ai-1:342`）却是一句**现役指路**：
「跑完自动存一张卡到**资源台 › 待分类**」。顺着这句去核落点，才看见报告卡的落点算式是一枚巧合。

## 一、缺陷：落点靠"库里的历史残留物"恰好正确

`shared/ai/reports.ts` 原来的算式（现已删除的 `hubDeck()`）：

```ts
const hub = (d.workspaces || []).find(w => w.kind === 'resource') || (d.workspaces || [])[0]
```

- `kind === 'resource'` 那枚 workspace 实体是 **R61 `migrateHubStructure()`** 给存量库建的（`id = CURATION_WS_ID`、名「资源台」）；
  V3.7.0 之后 store 的 `workspaces` getter 把它过滤掉了（`stores/app.ts:23-24`），但**原始数组里还在**。
- 所以存量库里这行代码返回 `zy-curation` ⇒ 落进资源卡池，看起来完全正确。
- 但 `defaults.ts` 新建库**不建**这枚实体（只有两枚策展台）⇒ 走的是 `|| (d.workspaces || [])[0]` 那个兜底，
  **新库第一张报告卡会落进「事业策展台」**，而回执照旧写「资源台 › 待分类」，用户按回执去找就找不到。
- 极端情形（库里一枚 workspace 都没有）落点 id 为空串 ⇒ 卡不属于任何台面，界面上任何列表都枚举不到它。

★这类"老库对、新库错"的缺陷静态门禁全盲：typecheck、build、1,569 条文本断言全都不看运行时选的是哪枚 id。
真正的问题不是那行代码写错，而是**它把落点建立在一枚本该由迁移退役的历史实体上**——
池不是 workspace 实体这件事（R179 起）没有在这条链上落实。

## 三、运行时凭据：直接执行真源码模块

`e2e.cjs` 跑的是打包后的扩展，chunk 导出名被 rollup 改写成单字母（实测 `export{I as c,b as f,...}`），
按名字 `import()` 拿不到 `saveReportCard`；而为这 2 行落点去搭一条 AI 抽屉 + 网关 + 复盘数据的链路，
成本与风险都不成比例（**边界如实见第六节**）。本轮用的是 **Vite dev 源模块探针**——dev 保留导出名，
所以能在浏览器里真正执行改动后的那个函数：

```
cd v2 && NODE_PATH=$PWD/node_modules node /tmp/zy_df3_dev_probe.cjs   # 需 npm run dev 在 :5173
```

实测（两种库形状各落一次卡，再重跑一次同名报告）：

| 项 | 新库形状（无 hub 实体） | 存量库形状（有 hub 实体） |
| --- | --- | --- |
| 新算式落点 workspaceId | `zy-curation` ✓ | `zy-curation` ✓ |
| categoryId | `''` ✓（待分类） | — |
| 回执 | `✓ 报告已存入 资源卡池 › 待分类「探针 每周回顾」…` | — |
| 同日重跑 | 张数 1→**1**、正文换成"正文二"、回执 `✓ 报告已刷新 资源卡池 › 待分类…` | — |
| **旧算式**（`hubDeck` 复现）会落到 | **`wsBiz`（事业策展台）** | `zy-curation` |
| 旧算式在零台库会落到 | **空 id ⇒ 孤儿卡，任何台面都不显示** | — |

同一枚常量、两种库形状，新算式给出同一个答案；旧算式在老库"对"、在新库把卡丢到别处——这就是本轮修的差。

## 四、判据 +2（1569 → 1571）+ 1 条标题随迁

- **★落点不许靠巧合**：`reports.ts` 的 `codeOnly` 必须同时出现 `import { CURATION_WS_ID }`、
  `workspaceId: CURATION_WS_ID`、`categoryId: ''`；`hubDeck` / `d.workspaces` / 正则 `kind\s*===\s*'resource'` 一律不许回流。
  ★负判据走 `codeOnly` 这条**当场量过**（不是想当然）：函数头那条 WHY 注释里就写着 `kind==='resource'`，
  裸 `read()` 命中＝判据恒假，`codeOnly` 不命中＝判据有效（实测 `raw true / codeOnly false`）。
  用正则而不是 `"kind === 'resource'"` 字面量，是因为只认一种空格的负判据等于给人留了改一个空格的绕行口子。
  另：卡自己的 `kind: 'resource'`（第 47 行，`ResourceCard.kind` 字段）不在此列——正则要 `===`，不会误伤。
  两条回执必须写「资源卡池 › 待分类」，且该地名在文件里**恰好两枚**（少一枚＝漏改一处，V2 变异专钉这条）。

- **★把 D-f2 给设置页加的"语境判据"扩到手册**：手册里每一枚「资源台」字样前后 20 字内必须有
  退役/作废/早期/曾经/下架/移除/不许/旧词，否则即"把退役物当现役去处指给用户"；
  「资源台 › 待分类」这个地名在手册与 `reports.ts` 两侧都负判据。
  ★这条正是抓出 `ai-1:342` 的那只手，现在把它写成门禁——D-f2 的教训是"枚举我改过的串"抓不到没改的，语境判据不依赖我先想到。
- **R148-6 标题随迁**（判据体一字未动）：它原本把落点写成"资源台待分类"，地名随迁为"资源卡池"，
  备案写明"落点算式本身由 R4-Df3 那两条钉"。

## 六、边界如实

1. **没给 `e2e.cjs` 加场景**，理由写清楚：打包后 chunk 导出名被改写（`export{I as c,…}`），
   按符号名动态 import 拿不到这个函数；要为 2 行落点铺一条"AI 接入 + 抽屉 + 周报数据"的运行时链，
   引入的脆弱比证明的多。池不变量的运行时凭据在别处已有（E2E-27 新建入池核 `台=zy-curation`、
   E2E-32 书签导入核 `落池=false`），本轮的落点凭据是上面那张 dev 源模块探针实测表，**探针在 /tmp、重启即失**，
   长期凭据是那两条文本判据 + 三次变异记录。
2. **没有删掉存量库里那枚 `zy-curation` workspace 实体**。它现在只剩"被历史迁移留下、被 getter 过滤"的状态，
   而删它属于数据迁移级动作（`curationProjections` 里的镜像引用、按台导出、回收站分区都按 id 找它），
   另立轮次做，不顺手。
3. **同款旧地名还有四处用户可见/AI 可见**，本轮没动，因为每一处都要单独判断改了会不会撞到别的系统：
   `airtable.ts:88`（推给 Airtable 的「所属工作台」列值就是「资源台」——改列值会让用户 Base 里
   按该列筛选/分组的视图当场失效，**要用户拍板**）、`usePyramid.ts:316,319`（toast 与镜像选择器里的「资源台」）、
   `CompassTree.vue:839`（树卡 peek「来源：资源台」）、`taskSupport.ts:104`（AI 投料把池写成「资源台」，模型会照抄进回答）。
   这四件合起来是下一刀 **R4-Df4 池的地名全站统一**。
4. `perf.cjs` 的指标名仍叫 `M11_切到资源台_首帧(ms)`，且被 R148-7 逐字钉着——内部指标名、不面向用户，
   记账不顺手改（改它要连 R148-7 的锚点一起搬）。
