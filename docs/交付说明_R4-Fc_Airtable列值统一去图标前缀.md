## 一、这一列原来有两种形态（为什么必须统一）

`Workspace.name` 的数据约定是「**icon + 空格 + 名称**」双写（图标另有 `icon` 字段，两份都存）。界面显示一律走 `shared/utils/wsName.ts` 的 `wsDisplayNameOf` / `wsNameById` 剥前缀（R129-B12 立口径、R4-Dg 收单源）。

**但同步引擎没走这一条**：

| 行 | 改前取法 | 推出去的值 |
|---|---|---|
| 台内资源卡 | `d.workspaces.find(w => w.id === r.workspaceId)?.name \|\| ''` | `💼 事业策展台`（带图标） |
| 镜像卡（投射落点台名） | `d.workspaces.find(w => w.id === p.targetWsId)?.name` | 同上 |
| 池卡 / 好奇心 / 任务 | 字面量 `POOL_DISPLAY_NAME` / `'调度台'` / `'方向台'` | 纯文字 |

⇒ **同一列两种形态**。本轮 E2E-44 在改前那一跑收下的真出网载荷：出网 3 行，其中 **2 行是 `🧪 探针策展台`**（台内卡与镜像行各一），1 行「资源卡池」。

为什么这不只是难看：该列类型是 `singleLineText`，用户在 Airtable 里按它筛选、分组、着色，或拿它跟别的表做关联时，**必须同时匹配两种写法**；而手册与设置页「同步范围」写的都是不带图标的那份——**界面与数据互相打脸**，与 R4-Di 当年那条（界面写「资源卡池」、推过去叫退役的「资源台」）是同一族病，这次差的是图标前缀。

## 二、改法：两处走已有的单源，不新造口径

```ts
// 台内卡
wsName: wsNameById(d.workspaces, r.workspaceId)
// 镜像行（落点台名）
const targetName = wsNameById(d.workspaces, p.targetWsId)
```

- `wsNameById` 的顺序是**先判池再落实体**（R4-Dg），所以：池卡仍显「资源卡池」；存量库里那枚 R61 留下的 `zy-curation` 实体（名字还叫「资源台」）不会再被当台名推出去；查不到的 id 返回空串 ⇒ 镜像行那句 `if (!targetName) continue`（落点台不存在就跳过该投影行）的语义**原样保留**。
- **没新增口径**：`POOL_DISPLAY_NAME` 仍全站只有一处定义；`wsNameWithIcon`（拼图标那把）被 R4-Fc① 的负锚钉成"只用于用户可选台去处下拉的 label"，不许进数据列。
- ★一处顺带的行为收敛（不是顺手改的，是同一处改动的必然结果）：若投射落点真是池（`targetWsId = zy-curation`，存量库数据里存在），改前推的是那枚实体的历史名「资源台」，现在推「资源卡池」。

## 三、运行时证据：E2E-44 量的是**离开机器那一列的值**

- **为什么源码断言不够**：`rowToFields` 之后还有拼装，静态文本只能证"取值走单源"，证不了"出网形态"。这条链此前在门禁里的覆盖是 R63-4/R64-3（源码字符串）+ E2E-34（改列名落库，不碰网络）——**真点同步并核载荷**是零。
- **取证姿势**：`page.route('**://api.airtable.com/**')` 挂桩（**零真网络、零真凭据**，PAT 写的是明桩 `pat-e2e-stub-only`），把 `POST`/`PATCH` 的 `fields` 逐条收进 Node 侧数组；桩对 `/meta/bases/` 返回 **15 列全名**——少一列 `ensureColumns` 就会去 `POST` 建列，那样测试本身就在改远端结构。
- **种什么**：一枚带图标的探针台（`name: '🧪 探针策展台', icon: '🧪'`）+ 一枚台内卡 + 一枚池卡并投射进那台 ⇒ 真点设置页「立即同步」⇒ 三格各自点名（台内卡 `探针策展台`、镜像行 `探针策展台`、池卡 `资源卡池`）并判「带图标前缀 0 行」。
- **两个方向都取到**：改前一跑红并报 `带图标前缀 2 行（["🧪 探针策展台","🧪 探针策展台"]）`；改后绿（E2E **44 / 0**）。
- **清场**：`launchPersistentContext('')` 每次跑都是临时新 profile，探针库随进程一起没——不碰任何真实用户数据，也不需要还原步骤。

## 四、判据：新增 2 条 + 随迁 1 条

- **R4-Fc①**（静态）：`wsNameById` 的两处正锚 + import 行正锚 + 两条负锚（ad-hoc `find(w => w.id === r.workspaceId|p.targetWsId)?.name` 不许回流；`wsNameWithIcon` 不许进这条链）。
- **R4-Fc②**（证据必须在跑）：锚 E2E-44 的四条腿——route  pattern 与 `atCells.push(r.fields)`、`iconRows.length === 0`、三格各自的 `cellOf(...) === …`、`fields: AT_FIELDS` 与桩凭据形状 `pat: 'pat-e2e-stub-only'`。★只判"有没有图标"会放过"整列取错字段"，所以三格分别点名。
- **R4-Di 随迁（一条被逐字锚点咬到的判据）**：它的正锚钉的是**整行** `import { POOL_DISPLAY_NAME } from '../utils/wsName'`，而这条 import 合法地长出了 `wsNameById` ⇒ 当场红。随迁是把锚收到"本条真正在守的那件事"（`const hubName = POOL_DISPLAY_NAME`、不许出现退役字面量），判据体其余一字未动，备案写进体内与标题。**这不是把判据调松**——它守的对象（池卡列值走单源）本轮仍然被钉着，只是不再钉那句 import 的拼写。
