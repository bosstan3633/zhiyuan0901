## 一、缺陷①：边界日当天的事件被陈旧快照冻住

**文件**：`D:\zhiyuan0904\v2\src\shared\utils\dailyStats.ts` · `mergeDailyStats()`

### 病根

原合并规则写的是「`k ≤ boundary` 时事件段换快照」。而 `boundary` 的定义是「事件日志里最早一条非 system 事件的日期」——它同时是**日志幸存起点**与**当日仍在增长的那一天**。

于是当天早些时候写过一次快照后，当天再发生的调出 / 采集 / 删除只存在于重建里（还没进快照），整段换快照会把它们**抹掉**。

### 用户可见症状

当天明明又调出了卡、又采集了卡，画像洞察页年度热力图「今天」那一格却**停在旧值不动**（调出数 u 归零、当日加权分不涨）。

### 实证

R176 离线复刻：esbuild 打包**产品真实实现** + 真实数据形状跑——

    重建今天 u=1 / w=2  ⇒  合并后 u=0 / w=1  ⇒  当天的新事件被陈旧快照冻住

### 修法

`k === boundary`（边界日当天）时**留重建**；`k < boundary`（严格早于边界日）仍换快照。

为什么「严格早于边界日才换快照」是对的：

- `k < boundary` 的日子，其事件**已经全部落过盘**（快照写过），重建只因日志淘汰而残缺 ⇒ 换快照是**补齐**，不是覆盖；
- `k == boundary` 的日子，快照只是**当天某个时刻的切片**，重建才是当前真相 ⇒ 留重建。

### 为什么不能改成「边界日取 max(快照, 重建)」

max 是逐字段比大小，而调出数 u 是**当日累计**（1 次变 2 次是增量，不是取大）。取大会把「今天 2 次调出」与「删 2 建 1」这类先后顺序事件算错。边界日当天「快照 ⊆ 重建」恒成立（重建含全部幸存事件），所以留重建既正确又无双计。

## 二、缺陷②：跨上下文写快照会抹掉别处刚补好的历史格子

**文件**：`D:\zhiyuan0904\v2\src\shared\storage\dailyStatsStore.ts`

### 病根

写路径用**本上下文的陈旧缓存** `snapCache` 合并后整棵写回。

### 双页探针实测复现

1. 上下文 A 打开画像页 → 读一次 `zy_daily_stats` → A 的缓存 = 当时的值（空）
2. 上下文 B（新标签页 / 浮层）写了一次快照 → 库里出现了新的一天 D1
3. A 回到策展台改一张卡 → 保存 → `writeDailyStatsNow` 用 A 的陈旧缓存（空）去 merge
   ⇒ 输出里根本没有 D1 ⇒ A 把整棵快照写回去 ⇒ **D1 被静默抹掉**

探针读数（修复前）：库里 `["2026-03-03"]` → A 写完后 `["2026-10-21"]`，D1 消失。

### 为什么这是「热力图褪色」的同一个病从另一个口子回来

R174-3 造快照是为了让老格子不被日志淘汰挤掉；结果这一写通道自己把别的上下文刚补好的格子抹了 ⇒ 用户看到的还是「老日子凭空消失」，而这次连日志里都没有线索。

### 修法

新增 `readLatestSnapshotForWrite()`：写前**重读库里的最新快照**。

- 写快照是低频动作（45s 时间闸 + 页隐藏补写），多一次 `chrome.storage.local.get` 的代价可忽略；
- 读回来的最新快照才是库里的真相 ⇒ merge 的输入完整 ⇒ 写出去也完整；
- **读失败退回 `snapCache`**，绝不把「读失败」误当成「库里没有快照」而空覆盖——退回 null 会用空覆盖，那是本缺陷的另一种形态；
- 坏快照不顶掉缓存；库里真没有才 `setDailySnapshotCache(null)`。

修复后探针：D1 仍在 `["2026-03-03","2026-10-21"]`。

## 三、E2E 门禁自身的随机漂移治理

### E2E-26 随机假红（本轮实测复现两次）

**现象**：同一份代码**第一轮全绿、第二轮 E2E-26 全项 false**（连「资源二级页」都没渲染）。

**根因**（三层叠加）：

1. `page.bringToFront()` 写在**导航之后**——但真正受害的恰恰是导航到二级页这一段（异步组件 chunk 拉取 + 挂载 + 定位高亮都在导航后发生）。页面处于后台时这段被拖到秒级；
2. 后面每一步（死等 1600ms → 点卡 → 死等 1500ms → 读抽屉 → 死等 2500ms → 读热度）都在「页面还没到」的状态下跑 ⇒ 必然全 false；
3. 判红时**看不出根因**——「二级页没上屏」有三种互斥可能（路由没切 / 渲染崩了 / 真没渲染），只看一个 boolean 分不清。

**修法**（判据强度一字未松，只把「等多久」改成「等到什么」）：

- `bringToFront()` **前移到导航之前**；
- 等 `.deck-page .pcp` 真上屏、等目标卡真渲染、等抽屉真打开、等事件日志与热度键**真落库**（用 `waitForLocator` / `waitForStorage` 助手）；
- 新增**诊断字段**（不进判定，只进 detail 字符串）：`url` / `renderError` / `deckCount` / `pcpCount` / 正文首屏文本 / `zy_error_log` 最近两条 ⇒ 判红时一眼看出根因。

**修复后**：连续多轮 E2E **44 通过 / 0 失败**。

### 浏览器解析缺陷（`v2/scripts/browser.cjs`）

Windows 下 `LOCALAPPDATA` 不总是真实用户目录——沙箱 / 应用虚拟化（AppContainer、MSIX 包）会把它重定向到 `…\AppData\Local\Packages\<pkg>\AC\`，而 playwright 的 Chromium 缓存仍装在真实用户目录。

症状：`cacheRoot()` 指向不存在目录 ⇒ 缓存回落整段失效 ⇒ 解析落到系统 Chrome ⇒ 新版 Chrome 不再支持 `--load-extension` ⇒ MV3 service worker 起不来 ⇒ E2E 第一条就超时（15s），报错只说「超时」，完全看不出真因是「浏览器解析错了」。

**修法**：Windows 下 `cacheRoot()` 返回**多候选根**（`LOCALAPPDATA` + 从 `USERPROFILE` 推的真实目录），逐个扫；`pinnedCandidates` / `anyCachedChromium` 同步兼容。
