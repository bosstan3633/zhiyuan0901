## 0. 一句话结论

产品在**功能正确性**上整体扎实（双向引用有防御性并集、软删/撤销口径自洽、Airtable 不回写、断点与降级都考虑过），
但存在**两处结构性硬伤**：

1. **导入路径完全不校验分类树结构** → 一条含环的 JSON 就能让资源台/策展台**永久卡死**，且无法用界面自救；
2. **导出与导入前自动备份把 Airtable 明文令牌一起写进本地文件** → 与你「数据主权 / 信得过」的定位直接冲突。

其余为局部功能错误与健壮性缺口。

## 1. P0 · 严重缺陷

### P0-1 分类树导入无结构校验 → 环状数据使页面永久卡死

**位置**
- `v2/src/newtab/views/Workspace.vue:1973`（策展台数据包导入的**唯一**校验）
- `v2/src/newtab/views/GlobalSettings.vue:1610`（全量导入的**唯一**校验）
- 无防护的递归/循环函数：
  - `v2/src/newtab/views/CurationCenter.vue:76-81` `nodeCount`（无 visited，递归）
  - `v2/src/newtab/views/CurationCenter.vue:48-53` `levelOf`（无 visited，`while` 循环）
  - `v2/src/newtab/views/CurationCenter.vue:58-63` `deepDescendantIds`（无 visited，递归）
  - `v2/src/newtab/views/Workspace.vue:1278-1283` `descendantIds`（无 visited，递归）
  - `v2/src/newtab/views/Workspace.vue:1376-1377`、`:1533` `levelOf`（无 visited，`while` 循环）

**代码**
```js
// Workspace.vue:1973  只认版本前缀
if (!ext || typeof ext !== 'object' || !String(ext.version || '').startsWith('2')) { … return }

// Workspace.vue:1278  无 visited 的递归
function descendantIds(catId: string): string[] {
  const out: string[] = []
  const walk = (pid: string) => { for (const c of wsCats.value.filter(x => x.parentId === pid)) { out.push(c.id); walk(c.id) } }
  walk(catId); return out
}

// CurationCenter.vue:48  无 visited 的上行循环
function levelOf(c: Category): number {
  let n = 1
  let cur = cats.value.find(x => x.id === c.parentId)
  while (cur) { n++; cur = cats.value.find(x => x.id === cur!.parentId) }
  return n
}
```

**问题**：两条导入路径都只校验 `version`，**不校验分类树的环 / 深度 / 孤儿父节点 / 数量上限**。
而 `mergeById` 用 `{ ...existing, ...incoming }` 合并，导入数据的 `parentId` 会直接覆盖现有值——**能造出环**。

**触发**：导入一份 `categories` 含互指父节点的 JSON，例如
```json
{ "version": 2, "categories": [
  { "id": "a", "name": "A", "parentId": "b" },
  { "id": "b", "name": "B", "parentId": "a" } ] }
```
（手工编辑、跨设备合并、文件损坏都可能产生。）

**后果**（按函数分两种，都致命）
- `nodeCount` / `descendantIds` → 无限递归 → **栈溢出异常**，页面渲染中断；
- `levelOf` 的 `while` 循环 → **标签页彻底冻结**（只能强杀进程）。

**恢复困难（这是它算 P0 的真正原因）**：
卡死发生在**分类树渲染/计数**路径上（`catAggCount` 在模板里被调用，`CurationCenter.vue:82-85`），
所以用户**打开不了资源台/该策展台** → 没有界面入口去删掉那条坏分类 → 只能清空扩展数据，**等于全部数据陪葬**。

**建议**
1. 抽一个 `validateCategoryTree(cats)`：DFS 带 `visited` 防环 + 深度 ≤ `MAX_CAT_LEVEL` + 孤儿 `parentId` 提根 + 节点数上限，两条导入路径都调；
2. **同时**给 5 个递归/循环函数加 `visited` 哨兵（纵深防御——数据侧校验挡不住已存在的坏数据）；
3. 顺手把 `pyLayout`（`Workspace.vue:1679`）的健壮性确认一下：它只从 `!parentId` 的根开始下钻，环内节点会被静默忽略——**不崩，但那些分类及其卡会凭空消失**，属数据静默丢失，也需一并处理。

## 2. P1 · 用户可感知

### P1-1 【安全/信任】导出与自动备份把 Airtable Personal Access Token 明文写盘

**位置**
- `v2/src/newtab/views/GlobalSettings.vue:1838-1846` `exportAll()`
- `v2/src/newtab/views/GlobalSettings.vue:1614`（导入前自动备份）
- 令牌字段：`v2/src/shared/models/index.ts:352` `airtableSync?: AirtableSyncState`、`:360` `pat: string`

**代码**
```js
// GlobalSettings.vue:1842
const payload = uiPrefs ? { ...d, uiPrefs } : { ...d }   // d = store.data!（整个 AppData）
downloadFile(`zhiyuan_backup_${dateStr()}.json`, JSON.stringify(payload, null, 2))

// GlobalSettings.vue:1614  每次导入都会执行
try { downloadFile(`zhiyuan_auto_backup_before_import_${dateStr()}.json`, JSON.stringify(store.data, null, 2)) } catch {}
```

**问题**：全量导出 = `AppData` 整体展开，而 `airtableSync.pat` 就在 `AppData` 里，**没有任何剥离逻辑**。
于是「导出数据」和「每次导入前自动备份」都会把用户的 Airtable 令牌**明文写进磁盘上的 JSON**。

**后果**：产品对外鼓励「导出即带走 / 数据包可分享」（03-4 帮助索引、02 销售材料均如此表述）。
用户把导出文件发给别人、传网盘、当"数据包"分享时 → **令牌随之泄露**，拿到的人可读写该用户的 Airtable Base。
这与「数据 100% 本机 / 信得过 / 不代持凭证」的信任承诺直接冲突，是本次审计里**唯一兼具安全后果与对外叙事矛盾**的问题。

**建议**
1. 导出时剥离敏感段：`const { airtableSync, ...safe } = d`，令牌与 `airtableMap` 一律不进导出文件；
2. 若确实需要"迁移同步配置"，做成显式勾选项（默认关）并在确认框明确警告；
3. 导入前自动备份**必须**同样剥离（它是最容易被忽略的一条，因为用户不会预期"我只是导入，怎么生成了一个含密码的文件"）。

### P1-3 任务采集浮层监听器泄漏 → 一次保存写入多条重复任务

**位置** `v2/src/content/overlay-impl.ts:1245-1249`（泄漏点）、`:235`（全文件**唯一**的 `removeEventListener`）

**代码**
```js
document.getElementById('__zy_tc_save__')?.addEventListener('click', saveTc)
const onTcKey = (e: KeyboardEvent) => {
  if (!document.getElementById('__zy_tc_save__')) return
  if (e.key === 'Enter' && (e.ctrlKey || e.metaKey)) { e.preventDefault(); e.stopPropagation(); saveTc() }
}
document.addEventListener('keydown', onTcKey, true)   // ← 局部闭包，永不移除
```

**问题**：`onTcKey` 是 `openTaskCapture` 内部的闭包，每次唤起都新建一个引用挂到 `document` 上，
而 `closeOverlay` 只做 `root.innerHTML = ''`（`overlay-impl.ts:222/234`）——**只清 DOM，不解绑 document 级监听**。
全文只有 `:235` 一处 `removeEventListener`，针对的是另一个函数 `onSavedKeydown`。

**后果**：同一页面会话内第 N 次唤起任务采集后，按 `Ctrl+Enter` 会触发 **N 个监听器同时调用 `saveTc()`**
（守卫 `getElementById('__zy_tc_save__')` 此时命中新浮层，拦不住旧监听器）→ **一次操作写入 N 条重复任务**。

**建议**：把 `onTcKey` 提为模块级具名函数（照 `onSavedKeydown` 的写法），在 `closeOverlay` 里
`document.removeEventListener('keydown', onTcKey, true)`；或统一改用 `AbortController` 的 `signal` 在关闭时批量解绑。

**复现**：卡标题 `AT&T`，搜索 `&` → `esc = 'AT&amp;T'`，`indexOf('&') = 2`，切 `slice(2, 3)` 得 `&`
→ 渲染成 `AT<mark>&</mark>amp;T`，用户看到 **`AT&amp;T`**。
修法：在原始 `title` 上定位、对切片分别转义；或转义后按转义结果长度对齐。
