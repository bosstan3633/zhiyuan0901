# 交付说明 · B7-d · D1 恢复即时 + 撤销（V3.8.39）

> 日期：2026-10-18 · 上一版 [V3.8.38](./交付说明_B7c_更新日志结构化_V3.8.38.md)

## 一句话

**回收站里按错了也能退回来**——五类恢复全部带「撤销」，撤销整笔回滚六个字段，恢复的那一行淡出 150ms 再离场。

## 规范原文与实际落地

规范 D1 原文两行：

> 恢复点击即生效 + Toast「已恢复到原位置 · 撤销」；卡片行恢复后本地淡出 150ms；筛选（类型/时间）保持收藏的断点行为。
> 验收：恢复有即时感知；撤销可用。

落地时撞上三件原文没写、但决定成败的事。

## 一、规范第三句指向了不存在的功能（否决）

原文要求「筛选（类型/时间）保持收藏的断点行为」。**核过源码：回收站既没有收藏，也没有时间筛选。**

| 检查项 | 结果 |
|---|---|
| `favorite` / `favorited` / `dateFrom` / `sortBy` / `filterBy` | 全文件零命中 |
| 实际的"筛选"形态 | 只有五个分区 tab（类型维度），无时间维度 |
| 断点行为的真实地基 | `RecycleBinView` 在 `App.vue` 的 `keep-alive include` 白名单里 |

回收站全页只有 363 行，唯一的分区切换是 `tab = ref<'res'|'task'|'curio'|'cat'|'arg'>`。

**处置**：不照抄。照抄等于在判据里写一条永远为真的假约束，或者真去造一个用户不需要的筛选器。
改为守真正存在的那份断点行为 —— **KeepAlive 白名单**（tab 跨路由切换不丢的地基，名字被移出白名单就静默失效），
并对「收藏 / 时间筛选」立**负锚**，防止后人照着规范真去造一个。

这是继 D3「30 天」之后，第二个「规范原文引用了产品里不存在的东西」的实例。

## 二、本批重心：撤销不是"把 deletedAt 塞回去"

这是本批最容易写成"看起来对"的错法。**一次恢复实际改了六处**：

| # | 字段 | 谁改的 | 漏掉的后果 |
|---|---|---|---|
| 1 | `deletedAt` | 恢复动作本身 | 这才是用户看得到的 |
| 2 | `updatedAt` | 恢复动作 | 排序与增量同步的时间锚错乱 |
| 3 | `workspaceId` | `rehomeIfOrphan`（R58-B1） | 卡留在别的台里 |
| 4 | `categoryId` | 同上 | 卡落在已删的分类下 |
| 5 | `metric.taskIds` | 恢复任务卡时回填 | **指标上挂着一个指向已软删任务的死 id** |
| 6 | `convertedAt` / `convertedTo` | 恢复好奇卡时清（R167） | 「已转化」计数与池内标记两头对不上 |

第 5 条最隐蔽：它正是 `sanitizeMetricTaskIds` 在**启动期**要消毒的那类脏数据 ——
却在「撤销 = 回到旧样」这条最该干净的路径上重新造了一遍。

**实现**：`RestoreSnap`（只读快照）+ `snapOf()`（必须在改动之前调用）+ `rollback()`（逐项还回）。

两条附带纪律：

- **按 id 回当前树定位**，不用闭包里的旧引用 —— 遵 REQ-030 口径（`persist` 后整树替换引用）。
- **撤销失败要如实说**。6 秒窗口里用户完全可能先永久删除同一张卡，此时若仍报「已撤销」，
  就是界面说成功、数据里卡却真没了 —— **回执撒谎比撤销失败严重得多**。批量恢复逐条计数并报实际条数。

## 三、恢复行淡出：为什么不能用纯 CSS 动画类

卡片一恢复，软删 `computed` 当场就不含它了，`v-for` 直接把 DOM 节点摘掉 —— **纯 CSS 的 `fade-out` 类根本没机会播**。

所以必须**本地多留一会儿**：把刚恢复的行塞进 `leaving` 缓冲，渲染时并进列表末尾（带 `.leaving` 样式），150ms 后真移除。

也**没有用 `<TransitionGroup>`**：它要求整块列表是稳定的 keyed 容器，而这里五个分区是 `v-if / v-else-if` 整块替换。
切 tab 时旧块被直接销毁、过渡钩子根本不跑（这本身是对的），但"行离场"发生在块内、与 TransitionGroup 的 diff 时序叠在一起，
很难证它每次都触发。自己控一份 `leaving` 缓冲，行为可读、可判据、也更好实拍。

### 合流视图的两条约束都不可省

```ts
function withLeaving<T extends { id: ID; deletedAt?: number }>(live: T[]): T[] {
  // ① 只并入不在 live 里的行 —— 否则同一张卡渲染两次
  // ② 缓冲行按原 deletedAt 插回原位 —— 直接 append 会让恢复中间行时
  //    它先跳到末尾再淡出，看起来像列表乱滚
}
```

排序锚点必须在 `deletedAt` 被清空**之前**取（`markLeaving(id, obj, at)` 的第三个参数），否则取不到值。

### 一条时序纪律

撤销时**先 `unmarkLeaving` 再 `rollback`**。反过来的话，卡还在 150ms 缓冲里，
用户看到的是「撤销了却什么都没回来」—— 功能都在、判据都绿，只有实拍才看得出来。

## 四、文案例外说清楚

规范示例是「已恢复到原位置 · 撤销」。但资源卡恢复时可能已被 `rehomeIfOrphan` 换台/换分类，
此时写「原位置」就是在骗用户；分类恢复更是明说了"其下卡片不会自动归位"。

**处置**：文案跟着 `rehomeIfOrphan` 的真实返回值走，有换台才提示，没有就不提示。
判据 `D1-7` 对「已恢复到原位置」立负锚。

四主题实拍里这条路径真的触发了：种子数据故意让资源卡的原策展台不存在，
回执如实显示「已移入『2027 考研』未分类」。

### 一个判据自身的坑：`fnBody` 曾给空白上锁

自建函数体提取器连续假红两次，两次都是**提取器把函数体认错了**，不是判据太严：

1. **TS 类型注解里的花括号**。`function restoreCat(c: { id: ID; deletedAt?: number })` 的第一个 `{` 是类型注解，
   不是函数体 → 配平提前闭合，`restoreCat` 只截到 53 字符（真身 200+）。
2. **泛型参数段**。`function withLeaving<T extends { id: ID; deletedAt?: number }>(live: T[])` 的泛型写在 `(` **之前**，
   自成一对花括号 → 深度计数错位一格，`withLeaving` 返回**空串**。

**一个会静默认错函数体的判据，等于给一段空白上了锁**：三条断言一起假红，而代码全是对的。
修法：从**签名闭合后**（先跳泛型、再对 `()` 配平）找函数体首。

> 顺带一条：`Category` 没有 `updatedAt`（不是 `CardBase`），所以快照类型按最宽结构声明，
> 回滚时字段缺失即跳过 —— **不给分类凭空造一个 `updatedAt`**。
