# 交付说明 · V3.8.42 发布（版本七处同步补做）

**日期**：2026-10-19
**性质**：不发新功能，只把「V3.8.42 这个版本到底存不存在」这件事说清楚。
**触发**：用户一句「最新版不应该是 v3.8.42 吗」——回仓核，**它不是**。

---

## 一、结论先给

**V3.8.42 的五个提交，一个都没改 `v2/src/manifest.ts`。**

而历史上**每个发布版本都有一次提交改它**：

| 版本 | 改 manifest 的提交 |
|---|---|
| V3.8.41 | `848f8bb` |
| V3.8.40 | `0b24925` |
| V3.8.39 | `8933e84` |
| … | 每个都有 |

⇒ **不是「批次代号 ≠ 发布版本」的设计，是漏了。**
我上一轮把它解释成"内部批次代号"，那个解释是错的——它推不出「为什么恰好每个正式版都改、唯独这五个没改」。

---

## 二、★为什么 1,973 条判据一条都没拦住

版本门禁守的是**不变量**：「七处写着同一个版本」。
`helpers.cjs` 的注释把这条写得非常清楚：

> 这些断言真正要守的是**「五处写着同一个版本」这个不变量**，不是「等于某年某版的固定值」。

**七处一起停在 3.8.41 时，它们彼此仍然一致。**
⇒ 不变量成立 ⇒ 全绿。

> **一致 ≠ 正确。**
> 一个只守「彼此一致」的守卫，管不了「该不该升」——那需要有人（或某条判据）知道**批次代号与发布版本的映射关系**，
> 而本项目没有这个映射：V3.8.42 从建立起就只是个 commit message 里的词。

**这不是判据的 bug，是判据的设计边界。** 补法有两种：
① 有人记得升（当前状态，靠流程）；
② 立一条判据：commit 用 `Vx.y.z` 开头 ⇒ manifest 必须等于 x.y.z。
本轮**没做 ②** —— 它需要一条读 git log 的判据，属于新增门禁，应由用户拍板，不在本轮授权内。
**记录在此，作为建议。**
