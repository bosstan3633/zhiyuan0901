## 三、★本轮六条新教训

### 1. ★★切片最容易坏在头部 require 解构块，而它在两片里行数不同

98 的解构块是 **7-8 两行**（`const {` 一行 + 内容行自带收尾 `}`），99 是 **5-7 三行**。取错行 ⇒ 98 丢 `const {` 与 `}` 当场 SyntaxError；99 更阴，**把断言体当 require 块拿进来，语法居然合法但语义已错**。
⇒ **切片前必须先 dump 该片 require 块的真实行号**，不能凭"通常是 1~3 行"的印象取，更不能 `sed -n '8p'` 硬取。

### 2. ★★"可独立加载"这个检查方式本身就是错的

分片里的 `check()` 在 **被 require 的那一刻就执行**。用子进程 `require` 一片做校验 ⇒ **判据递归调用自己**（本片被自己判红报"未知错误"，而单独 require 本片能正常打印全绿）。
⇒ 语法层检查必须用 `vm.Script` **只编译不执行**，天然无副作用。副作用：80s → 15s。

### 3. ★★`git add` 要放在最后，不能放在生成文件之后

本轮先 `git add` 了语法还坏的 98b，后续修正被 `git checkout` 覆盖回坏版本，引发一次加载期崩 + 一次 R4-Dm ENOENT 误红（`__B8_orphan_probe__` 探针早已由 B8-2b 的 `finally` 正确清理，**与本次改动无关**，是坏 require 让 98b 提前崩溃的连带现象）。
⇒ 与既有纪律「撤销必须整笔快照-回滚」同源：**任何 git 写操作前先确认文件内容是对的**。

### 4. ★★搬代码前必须先查「有没有判据在读被搬走的那段正文」

本轮搬 overlay 样式**没做这一步**，结果 R77 / R93 / R105 / B14 / D3 / D7 等 **16 条判据同时红**，红得看不出真因（症状像"浮层样式被谁改了"）。
V3.8.41 刚为 ReviewPanel 删文件立过同款纪律，本轮又踩了一次 —— **说明它必须前移到"搬"这个动作之前，而不只是"删"之前**。

### 5. ★★负锚在聚合下会放大：「某字面量在全文件里不存在」≠「在某处不存在」

`R78-2` 的负锚原是全文件 `!o.includes(", 5000)")`。overlay-impl 改为返回 content 全量聚合后，DOM 节点清理里那个**真·无关**的 `setTimeout(…, 5000)`（`el.remove` 兜底）被聚合进来，负锚当场咬自己。
修法按既有纪律「豁免条件必须逐个旧值对齐它出现那一句的语义」：把范围收到**回执那一句**。
★修的过程中我第一版还写了个 `![0-9]{4,}` 想"更通用"，结果它**匹配了 2500 自己** —— 负锚加码也是负锚的一种错法。

### 6. ★判据编号要先查占用

新写的两条我编号 P0-S7 / P0-S8，而 **P0-S7 已被"内联视觉样式棘轮"占用**（在同一个文件的更早位置）⇒ 改判 S9 / S10。编号冲突不会报错，只会让人以为有两条同号判据而找不到。
