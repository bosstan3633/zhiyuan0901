## 一、先更正我自己：那条旗标是错的，撤了

R4-Fd 的结论是「池卡列表那 368 px 是文字 AA 模式差（LCD 子像素 vs 灰度），加 `--disable-lcd-text` 钉掉」。**这个结论不成立**，错因很具体：

- 我拿来当证据的那次"同构建两跑 0 差"，用的是 `--only=notion`（单主题 26 张）；
- 而**同一轮**我又量过另一条事实：单主题跑与全量跑**不可互比**（dz-*/settings 那批差 9,676–205,668 px，会话顺序影响画面）。
- 两条放在一起，前者就不能当证据用。

R4-Fe 用**全量两跑**复测（都带旗标）：`notion-deck-pool-list` 仍然差 **368 px**、色偏仍然只在一侧（A=0 B=376）⇒ 旗标压不住它 ⇒ **撤**，并把这段错原样记在 `theme-audit` 的 args 上方（判据 R4-Fd① 现在正钉着"这条注释必须在、旗标不许回流到代码里"）。

那这族到底是什么？补上决定性的一步之后才敢下结论：

> **104 张图**在两次全量跑之间的 `scene-state.json` 取样点（元素几何 + 计算样式）**逐点全同**，像素却仍然差。

⇒ DOM 与样式层没有任何变化，差异发生在**光栅化层**（Chromium 侧的非确定性）。同族在 raycast 主题也出现：372 个抖动像素摊在 262 行、幅度只有 4、`hardPixels=0`，只因带宽超 8 行才落进"变化"档。
所以这一族的处置不是"修好它"，而是：**红的时候由 `--why` 直接告诉你 DOM 态一致 ⇒ 别再翻结构与 CSS**。要不要为它放宽阈值，是尺子灵敏度的取舍，我没有自己动手改（见 #132，三选项与推荐都写在里面）。

## 二、把「DOM 态」接进像素归因（这条是本轮真正的增量）

R4-Fd 的 `--why` 只回答"像素像哪一类"；现在它会多说一句"那一刻的 DOM 一样吗"：

```
✗ raycast-deck-pool-list.png   变化像素 0  抖动 372  差异带高 262 行  单通道最大差 4
    └ 归因：取样框内已无变化像素（包围盒取整边界）
       位移抵消 变化像素 0→0（最佳位移 0,0）｜ 带色偏像素 A=372 B=371｜差异行数 4｜幅度 4
       DOM 态：一致（scene-state 各取样点的元素几何与计算样式逐点全同）⇒ 差异只在光栅层，别再翻结构与 CSS
```

- **theme-audit 侧**：每张截图当场记 4 个取样点的元素链（`cls / y / h / border / background / opacity / transform`）+ `scrollY` + 文档高，与图同目录写 `scene-state.json`。取样点不是随手挑的：`(720,58)` 手册页分界线本身、`(720,120)` **分界下方**（整片挪 1px 只有采下方才看得见——我第一版只采了分界上那一个点，那样两跑会"看起来一样"，错过 #127 的形态）、`(940,859)` 设置页标签区那条 1 行的线、`(280,500)` 池卡列表胶囊。
- **img-diff 侧**：两侧目录都有 `scene-state.json` 时，红图自动分「DOM 态一致 ⇒ 光栅层」与「不一致 ⇒ 点名哪一层、y/h/border 各是多少」。

★**修了自己工具的两处失明**（都是本轮实测里暴露的，不是顺手清理）：
1. `--why` 的进入条件是 `r.hardBBox` 存在，于是 **`hardPixels=0` 但带宽超标的红图根本不进归因分支**——raycast 那张 372 px 红了却没有一句解释。改成 `r.hardBBox || r.bbox`。
2. 日志里 `场景几何记账：N 张图的 3 个取样点` 的"3"是写死的，取样点加到 4 个之后它就开始**报假数**。改成 `STATE_PTS.length` 现算。（同类形状本轮还有一处：`--why` 文案里我原先写死"三个取样点"，也去掉了数字。）
3. 还有一条纪律性发现：**R4-Fd 的 scene-state 只包在主页面截图上**，104 张里只覆盖 96 张，于是 `apple-ov-search` 那条 1 行 / 幅度 30 的差**没有任何活证据可查**。现在 `ovPage.screenshot` 也包上（判据 R4-Fe① 钉"两个包装都得挂"）。这就是"证据面比断言窄"的老形状，本轮第三次遇到。

## 七、边界如实

1. **本轮没有"消灭"任何一族跳变**，只是把一条错的处置撤掉、并给红图配上 DOM 态证据。池卡列表那一族仍在，且我现在的结论是"光栅层非确定性"——它可能压根不可钉，只能被解释。
2. **"光栅层"是排除法得到的，不是正面测到的**：证据是"像素差 + DOM/样式逐点全同"。取样点只有 4 个，理论上存在"变化发生在取样点之外"的可能（比如某个未采到的元素改了背景）。要正面钉死需要像素级 DOM 对照（把两跑的整树几何+样式全量比），本轮没做。
3. **#132 是取舍，我没替用户拍**：现状是"同一份产物两跑，每 2–3 对里就有 1 张红"，靠 `--why` 解释；放宽带宽档或提高 HARD 都能减少假红，但都在削这条尺子存在的意义（宁可红也不放过）。
4. **`--why` 仍然不改判**：所有红图照旧让 `img-diff` 非零退出（R4-Fd③ 钉着），归因只是多说一句话。
5. **阈值（20% / ≤12 / ≥30）与 4 个取样点都是这台 Mac、这一份 Chromium、这 104 个场景的量**，换机或大改取景后要重量。
6. **`--only=<theme>` 的产物不要写进基线目录**（本轮又用了一次它做快速对照，但写盘都落在独立 tag 且已删）。这条纪律目前只写在注释与本文里，**没有判据守着**——它约束的是人的操作，不是代码形态。
