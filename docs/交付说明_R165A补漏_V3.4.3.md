## 二、③ 落地即抓到两个真缺陷（这是本轮最值钱的部分）

把 entry-literals 接进实跑后，**第一次跑就红**，顺藤出两个洞：

1. **R165-A 的豁免在 Windows 上是静默空操作**。原写法
   `path.relative(root, f) !== 'src/shared/storage/keys.ts'`——Windows 下 `path.relative` 返回**反斜杠**
   （`src\shared\storage\keys.ts`），与正斜杠字符串**永不相等** ⇒ 豁免从未生效。
   Mac 正常、Windows 恒红；而这条门禁在 Windows 从没被实跑过，所以两轮验收全绿通过、无人发现。
   修法：改**绝对路径比较**（`f === path.join(SRC, 'shared', 'storage', 'keys.ts')`），并在 R165-A9 里
   反向钉死「不得再用 `path.relative(...) === 'src/...'` 这种写法」。
2. **该红本身自 R159 潜伏**：R159 键字典 + R164 键边界把 `zy_ai_v1` 登记进 `K`，而 `keys.ts` 本在入口闭包
   ⇒ 键名字面量必进入口闭包扫描。R164 / R165-A 两轮的门禁清单都没跑这个脚本。

> **通则（已写进 06-2 §B）**：凡是"独立脚本型门禁"，**必须有一条回归断言真的 spawn 它并看退出码**。
> 只断言"脚本里有某些字"，等于没有门禁——本轮两个缺陷都是这么藏住的。
