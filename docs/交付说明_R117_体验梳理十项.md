## 一、六主题域落地（A–F）

### A · 分类口径统一（① ②）

**根因**：采集浮层（`content/overlay-impl.ts`）、资源台批量移动（`composables/useWorkspaceBatch.ts`）、全局采集（`components/GlobalPopups.vue`）三处**各自实现分类下拉**，且**都漏了 `deletedAt` 过滤** —— 软删分类（幽灵项）与同名历史记录照常进下拉，用户截图里「产品设计 / 效率工具 / 事业策展台」各重复 3 次即由此而来。资源台侧（`Workspace.vue` 的 `wsCats`）口径本来就是对的。

**处置**：新增 `shared/utils/catTree.ts#buildCatOptions(cats, { sep? })` 作为**分类下拉选项的唯一口径** —— 过滤软删 → 建 `byId` 索引 → **孤儿/自引用提根** → 带 `visited` 的防环 DFS → 稳定排序（`order`）。三处调用方切换为本函数（浮层用路径式 `sep: ' / '`，批量移动用缩进式 `└`，与各自原视觉一致）。

### B · 定位与高亮统一（⑤ ⑥）

**根因**：定位**生产端 3 份重复实现**（`CompassHome.locateRec` / `GlobalSettings.openStatCard` / `GlobalPopups.openItem` + `runFlatLocator`），且语义只到「切台 + 高亮」；其中 `openStatCard` 对任务卡跳 `/` 而消费者住方向台 ⇒ **跳过去既不定位也不高亮**（真 bug）。搜索点击对带外链的资源卡**直接外开浏览器**，与「定位到资源台位置」的诉求相反。

**处置**：
1. 新增 `shared/utils/locate.ts`：`locateTargetOf(d, kind, id)` 一处计算路由目标，`asLocateKind()` 归一旧 kind 串，`LOCATE_HK` 为卡型短码表。
2. **query 三件套**：`hl` = 目标卡 id · `hk` = 卡型短码（`res`/`task`/`curio`，消费端**按 kind 认领**，消除调度台同页「任务卡与好奇卡两个 `?hl` 消费者」竞态）· `cat` = 资源卡所在分类（先切分类再滚动，实现「定位到具体位置」）。
3. **增量渲染前置**（R112/R116 引入 `RENDER_STEP=80` / `KANBAN_COL_STEP=20` 后的必踩坑）：目标卡可能不在已渲染集里 → 定位前先 `ensureCardRendered` 把该卡纳入渲染集，再 `scrollIntoView`；否则**静默失败**。
4. 搜索点击语义反转：默认「定位」，外开降级为行内显式入口。

### D · 字段配置真实生效（⑦）

**根因**：配置读写链路是通的，但**取值口径分裂** —— 任务卡的状态/项目/指标/日期、好奇卡的问题/状态/来源等**骨架字段硬编码渲染**，设置里关掉照样显示（用户报「设置无效」）；扩展行还被 `slice(0,4)` 截断并把 `description` 排除。

**处置**：三卡骨架字段一律改由 `visibleFields(kind)` 判定后再渲染（任务卡引入 `tShow(key)` + `T_SKELETON_KEYS` 去重；好奇卡同理）；取消扩展行截断与 `description` 排除。`fmtCardDate` 入参放宽到 `number | string`（`dueDate` 是 ISO 串）并加无效日期守卫。

### E · 生命周期阈值可配（③）

**处置**：模型加**可选**字段 `CardBase.coolingDays?: number`（**零迁移**）；`lifecycle.ts` 加 `DEFAULT_COOLING_DAYS=30` / `ARCHIVE_RATIO=3` / `coolingDaysOf` / `coolingMsOf` / `archiveMsOf` / `hasCustomThreshold` / `setCoolingDays`。**用户只填一个冷却天数，归档阈值按 3 倍自动推算**（3:1 正是原 30:90 的比例，避免两个阈值互相打架），夹取 1–365 天。出厂默认仍是 30/90。`snoozeCard` 的「忽略一个评估周期」改为跟随该卡自定义冷却天数（`coolingMsOf`），仍**不碰 `lastCalledAt`/`updatedAt`**（R113-T9 热度统计零污染不回退）。
