## 二、REQ-045 搜索交互固化

### 2.1 用户反馈的两个 Bug（先诊断，后固化）

**Bug 1 · 第三方页单击无反应（根因已找到）**
> 在非工作台标签页（第三方网页）搜索后单击结果，没有跳转到工作台并定位。

**根因**：content 浮层单击发的消息类型是 `zy-route`（第卅六轮引入），但 **background 的 onMessage 监听器只有 `zy-locate-workspace` 和 `zy-open-route` 两个分支，从来没有 `zy-route` 分支**——这条消息直接落空，从未生效过。而 newtab 内弹层走的是 router.push 同上下文，所以"newtab 内能开抽屉、第三方页不能"。

**修复**：`openSearchLocator` 改用 `zy-open-route`（background 已有处理），并给 `handleOpenRoute` 增加 **drawer 透传**：`{type:'zy-route', route, drawer}` → App.vue 收到后 push 路由 + 打开抽屉（第卅六轮逻辑已有）。

**Bug 2 · 双击无反应（事件竞态）**
> 双击结果没有任何反应。

**根因**：单击和双击绑定在同一个元素上。双击 = 第一次 click + 第二次 click + dblclick。第一次 click 就执行了定位并 **closeOverlay()**（浮层关闭、DOM 移除），后续的 dblclick 找不到元素 → 无反应。

**修复**：单击/双击统一走"开链接"逻辑 + **300ms 同项去重**——单击开一次；双击时第二次 click 与 dblclick 均被去重拦截，只开一次。

### 2.2 固化的交互规范（双入口统一）

| 操作 | 行为 |
|---|---|
| **单击** / **Enter** | 直接打开链接（URL / 本地文件 / Obsidian）；**无链接** → 定位到卡片所在工作台/罗盘并高亮 |
| **Ctrl+Enter** | 无论有无链接，**定位到卡片所在处 + 打开详情抽屉** |
| **双击** | 开链接（与单击一致，去重防双开） |

**双入口同步**：content 浮层（第三方页）与 newtab 弹层（`Ctrl+K`）行为完全一致；第三方页的定位走 background → 新开/聚焦工作台标签 → 落地展开抽屉。

### 2.3 改动明细

| 文件 | 改动 |
|---|---|
| `content/search-overlay.ts` | 单击/双击 → `openSearchResult`（开链接）+ 300ms 去重；Enter=开链接、Ctrl+Enter=`openSearchLocator`；`openSearchLocator` 改用 `zy-open-route` + drawer；title 提示更新 |
| `background/index.ts` | `zy-open-route` 支持可选 `drawer` 透传给宿主 newtab |
| `GlobalPopups.vue` | 单击/双击 → `selectResult`（开链接）；Enter=`runFlat`、Ctrl+Enter=`runFlatLocator`；`openItem` 加 300ms 去重；删除死代码 `selectResultLocator` |

## 三、REQ-046 交互响应速度优化（速度第一）

### 3.1 已落地的优化

| 优化 | 改动 | 收益 |
|---|---|---|
| **结果渲染限流** | 两个搜索入口每组最多渲染 **30 条**，超出显示「… 还有 N 条，输入更精确的关键词」 | 千卡级宽泛搜索（如输入"a"）不再一次性渲染几百个 DOM 节点，首屏毫秒级 |
| **输入防抖调优** | content 浮层搜索防抖 90ms → **60ms** | 键盘响应更跟手 |

### 3.2 链路核查结论（已优，无需再动）

| 环节 | 现状 | 结论 |
|---|---|---|
| content 数据读取 | `dataCache`（1.5s TTL）+ `onChanged` 实时同步，每次按键不再读 storage | ✅ 已优 |
| 搜索匹配 | 关联 Map 化（ws/cat/proj 名称 O(1) 查找）；拼音匹配在文本命中时短路跳过 | ✅ 已优 |
| 结果分组 | 单次 for 归桶（R34-18），无 filter+indexOf 嵌套 | ✅ 已优 |
| newtab 搜索 | `filteredResults` computed 全量过滤+稳定排序，千卡级毫秒完成（Vue 缓存） | ✅ 可接受 |
| 保存写入 | 防抖合并 + 自写标记跳过全树替换 | ✅ 已优 |

### 3.3 明确不做（及原因）

- **虚拟滚动**（Workspace 千卡列表）：改动面大、回归风险高，且当前千卡级实测流畅，等卡数到万级再评估；
- **搜索输入防抖**（newtab 弹层）：Vue computed 毫秒级重算，加防抖反而引入"输入滞后感"，违背速度第一。

## 四、REQ-047 本地图片/HTML 上传 · 技术调研报告（待拍板）

### 4.1 需求还原

把本地图片 / HTML 文件上传到资源卡/好奇心卡/任务卡下，点击打开时：**图片弹窗预览、HTML 在浏览器新标签页打开**。

### 4.2 可行性结论：**可行，但绝不能存进 chrome.storage.local**

用户问得对——这会直接击穿存储与速度。逐条说清楚：

| 维度 | chrome.storage.local（现状） | IndexedDB（建议路线） |
|---|---|---|
| 上限 | `unlimitedStorage` 已解除 10MB 限制，但**浏览器磁盘配额仍在**（实际可用几十~几百 MB，受磁盘与 Chrome 配额影响） | 独立于 storage，同样受磁盘配额但容量规划更清晰 |
| 读写模型 | 每次 `set()` 都是**整树 JSON 序列化**。100MB 数据 → 每次保存 serialize + 写盘，**卡顿秒级**；每次启动读全树 → 打开速度崩 | **按 key 读写**，图片/HTML 单独存 Blob，读写 O(1)，不影响主数据树 |
| 跨页同步 | `onChanged` 全量替换 data 引用 → 100MB 会触发全树 diff/重渲染风暴 | 图片 blob 与主数据分离，主树依旧轻量 |
| 内存 | 图片 base64 进 JSON 后体积再膨胀 ~33%，且常驻内存 | Blob 可懒加载，点开才解码 |

**核心结论**：
1. **如果图片/HTML 塞进 `zy_data_v2` JSON**（把 base64 存字段里）→ 数据量几百 MB 后，**每次防抖保存、每次启动、每次跨页同步都会卡**，打开速度必然劣化——**这个做法不可行**，与用户"影响速度就不做"的判断一致。
2. **如果走 IndexedDB**（图片/HTML 以 Blob 单独入库，卡片只存 `{assetId, type, size}` 引用）→ 主数据树保持轻量（KB 级），图片按需读取，**对打开/交互速度影响可忽略**。技术完全可行：MV3 支持 IndexedDB；`<img>` 用 `URL.createObjectURL(blob)` 弹窗预览；HTML 用 `Blob` → `URL.createObjectURL` 在浏览器新标签打开（或存为 `data:` 链接）。
3. **本地文件型资源已有现成路径**：`linkType='file'` + 完整路径 + 开启「允许访问文件网址」即可双击打开本地图片/HTML——不需要上传。上传的价值在于**随 JSON 一起导出/迁移**（便携性）。

### 4.3 建议方案（若拍板做）

- 模型：ResourceCard/CuriosityCard/TaskCard 新增 `assets?: { id: string; kind: 'image'|'html'; name: string; size: number; mime: string }[]`
- 存储：`chrome.storage.local` 之外开 IndexedDB 库 `zy_assets`，key = assetId，value = Blob
- 交互：卡片菜单「📎 附件」→ 选择图片/HTML → 上传（读文件 → 存 IndexedDB → 写引用）；卡片上附件 chip 点击：图片 → 弹窗预览（createObjectURL），HTML → 新标签打开
- 导出/导入：导出 JSON 时把附件一并打包（或单独导出 assets 目录 zip）
- 容量护栏：设置页显示附件总占用；单文件上限（如 20MB）；总数上限可配置
- **性能护栏（速度第一）**：主数据树绝不存 base64；附件全部 IndexedDB 按需读；卡片列表只显示附件元数据（名称+大小），不解码

### 4.4 对用户问题的直接回答

> "是否可以将本地的图片、html 文件，上传到某个资源卡/好奇心卡/任务卡下面…"

**可以**，但前提是附件走 IndexedDB 而非塞进主 JSON——否则数据几百 MB 后**打开和交互速度必然劣化**（整树序列化/同步/启动都是灾难）。

> "如果影响，那么这个功能就暂时不做"

按上面的建议路线，**对主链路速度无影响**，所以可以做；如果按"塞 storage"的土办法做，**必然影响，那就该不做**。

### 4.5 拍板结论（2026-09-02 用户确认）

| 决策 | 结果 |

| REQ-047 附件功能 | ✅ **立项，做最小版本**（图片上传+弹窗预览、自包含 HTML 上传+新标签打开），计划排入 **第卅九轮 V2.15** |
