## 二、④ 性能量账（用户反馈：本版切换/调度不如上一版）

**先量后修，两组量具对照 v3.6.1 真基线（worktree+junction，`C:\Users\win\r169-base`）**：

**perf.cjs 交错 2 轮（同批最小值口径）**：M1 2434 vs 2070ms · M2b 426 vs 402ms · M10 sync 15.7 vs 16.8ms / 阻塞 0 vs 0 · M7 开详情 sync 0.5 vs 0.3ms —— **切换/开详情在仪器指标上同档**；唯 M2a（切资源台）A 侧两轮都偏高（715 vs 214ms）。

**perf-census 真库逐动作账（不受噪声影响的量，各 2 轮）**：

| 动作 | B=V3.6.1 | A=V3.6.2 | 判定 |
|---|---|---|---|
| 基线·调度台首页 | 0 长任务 | 0 长任务 | 无差异 |
| 冷挂资源台 | [438,1098]=1536ms | [424,868,413]=1705ms | +170ms，噪声带内；**~1.1s 长任务两版都有** |
| 回调度台 | 123ms | 152/177ms | +42ms 方向一致 |
| 再进资源台(keep-alive) | 592ms | 647/653ms | +58ms 方向一致 |
| 常驻抽屉 | 1 个 | **0 个** | R169 合并红利 |
| DOM 冷挂增量 | +419 | +343 | R169 反而更省 |

**结论（诚实口径）**：
1. **体感回退的大头是环境**：同一个 V3.6.1 包在 R168 采样日冷挂资源台阻塞只有 **283ms**，今天同包实测 **1536ms** ⇒ 本机今日整体慢 ~5 倍（与 EBUSY 策略同日出现，疑似安全软件实时扫描升级）。这不是 V3.6.2 的代码回退。
2. R169 特有净差只有 **+40~170ms/动作**（回调度台 +42、keep-alive +58），无单点 ≥500ms 的结构性回退项可修；列窗口滚动处理器核查为零开销（一次比较）。
3. **本轮不盲修**（拍板④节奏）：没有量得出来的"最高回退项"。**静置时段复采定谳**（老账⑥，基线已留存）：若静置后 M2a/census 仍显示 A 侧一致劣化 >2×，R171 上方向台切换专用探针深挖（现量具未覆盖方向台切换动作，已记缺口）。

### ⚠ 本轮最贵的排障：视觉走查「资源卡详情」4 主题全败 → 工具盲区（非产品回退）

现象：drawer-resource 镜头 `.res-card` 恒命中 0，4 主题复现；同主题台面资源台图 ✓、任务/好奇抽屉 ✓。探针双包判别：**v3.6.1 基线同样失败** ⇒ 纯工具链问题。根因链：

1. audit 在 boot **之后**注入 `zy_ui_v2`；`mergeExternalUIPrefs`（R128-A1）合并时**替换 uiCache 对象**，而运行中的 `store.ui` 持有旧引用 ⇒ 注入的 `wsViewMode: card` 永远到不了应用；
2. 真库存在 **4 张脏 `isThesis` 卡**（历史操作遗留），`curationMetrics` 取第一张 ⇒ 无偏好时默认视图回落**金字塔**（R84 W2-② 设计行为）⇒ 卡片网格不渲染；
3. R169 当时通过属时序运气。修复：注入后「记 hash → reload → 写回 hash」强制 boot 重读偏好（R161 reload 丢 hash 坑闭环）；R170-4 断言钉死该时序。
4. **产品侧无恙**（用户正常 boot 路径读得到偏好）；「真库 4 张脏 isThesis 卡」记 R171 观察项（多张 isThesis 并存时 metrics 取首张，建议提供清理入口或导入时去重）。
