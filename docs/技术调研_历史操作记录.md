> 第卌四轮调研 · 2026-09-03 · 状态：**待拍板，未动工**

## 0. 一句话结论

**✅ 完全可以实现，且成本很低。** 关键发现：三种卡片（资源/任务/好奇心）的公共基底 `CardBase` 已经自带 `createdAt / updatedAt / deletedAt` 三个时间戳，删除全部走软删除——**"什么时间新增、什么时间删除"这两类历史，现有数据里已经完整存在，不需要新建任何写入链路**。主要工作量在设置页的"历史记录"展示章节 + 汇总统计 + CSV 导出。

## 2. 现状核查（代码实证）

### 2.1 数据层——历史已经存在 ✅

`v2/src/shared/models/index.ts` L108-126 `CardBase`（三卡公共基底）：

```ts
export interface CardBase {
  id: ID
  kind: 'resource' | 'task' | 'curiosity'   // 卡片类型自带
  ...
  createdAt: number     // ← 新增时间：所有卡都有
  updatedAt: number
  deletedAt?: number    // ← 删除时间：软删除标记，回收站恢复时清除
}
```

- **新增历史** = `createdAt`，三卡 100% 覆盖。
- **删除历史** = `deletedAt`，软删除后卡片仍留在主数据里（回收站可恢复），删除时间戳不丢。
- 存量数据（317+ 张卡）全部兼容，**不需要迁移**。

### 2.2 两个纯派生方案覆盖不了的缺口 ⚠️

| 缺口 | 场景 | 影响 |
|------|------|------|
| **永久删除（purge）** | 回收站里点"永久删除"或"清空回收站"（RecycleBin.vue L79-140），卡片从主数据中物理移除 | `deletedAt` 随卡片一起消失，这条删除历史丢失 |
| **回收站恢复** | 恢复时 `deletedAt` 被清除 | 派生视图会显示该卡"从未删除过"（恢复动作无痕） |

是否需要堵这两个缺口 → 见方案 B 和拍板点 Q-1。

### 2.3 可复用的现成能力 ✅

- **CSV 下载链路**：`GlobalSettings.vue` L930 `exportCsvForWorkspace()` 已实现 UTF-8 + BOM（`\uFEFF`）CSV 下载，Airtable 直接导入无乱码——历史明细导出照抄此链路。
- **设置页分章结构**：GlobalSettings 已有"导入数据 / 导出数据 / 危险操作 / 关于"等分页章节，新增"历史记录"章节是纯增量，不动现有代码。
- **汇总统计**：全部可从三卡数组 reduce 派生，无需新增存储。

## 3. 技术方案

### 方案 A：纯派生（零新存储）

新增 `historyDerived.ts` 工具：每次进入"历史记录"页时，从 store 实时扫描三卡数组 →

```
events = [
  ...三卡.map(c => ({ ts: c.createdAt, action: '新增', kind: c.kind, card: c })),
  ...三卡.filter(c => c.deletedAt).map(c => ({ ts: c.deletedAt, action: '删除', kind: c.kind, card: c })),
].sort((a,b) => b.ts - a.ts)
```

- 汇总五指标同理派生：总卡片数（非 deletedAt）、今日/本周新增（createdAt ≥ 今日0点 / 本周一0点）、今日/本周删除（deletedAt ≥ 阈值）。
- 优点：**零存储、零写入链路、零迁移、存量数据立即生效**。
- 缺点：purge 后删除历史丢失、恢复动作无痕（见 2.2）。
- 工作量：约 **1 天**（工具函数 0.5 + 设置页 UI 0.5）。

### 方案 B：轻量事件日志（在 A 之上叠加，推荐）

新增 append-only 事件日志 `zy_event_log`（chrome.storage.local 独立 key，**不混入** `zy_data_v2` 主 JSON）：

```ts
interface HistoryEvent {
  ts: number
  action: 'create' | 'delete' | 'restore' | 'purge'
  kind: 'resource' | 'task' | 'curiosity'
  id: ID
  title: string        // 事件发生时的标题快照（purge 后仍可显示）
  detail?: string      // 描述摘要（截断 120 字）
}
```

- 写入点仅 4 处：创建卡 / 软删 / 回收站恢复 / 回收站永久删除，各 append 一行，共约 20 行代码。
- purge 后历史**仍在**（标题快照保住了），恢复动作也有痕迹。
- 容量：每条约 120 字节，**5000 条滚动淘汰上限 ≈ 0.6MB**，对 chrome.storage（10MB 级）无压力；超过则丢最旧。
- 工作量：方案 A 基础上 +0.5 天，合计 **1.5 天**。
- 存量数据：日志为空时自动回退方案 A 派生（历史记录页对旧卡仍然完整可用），新旧无缝。

- Airtable 导入：时间列自动识别为日期，动作/类型可建为单选。

## 4. 边界与不做的事

- **不记录编辑历史**（需求明确只要新增/删除；编辑历史需全文快照，成本高收益低，后置）。
- **不记录打开/浏览**（stats.lastVisits 已有打开统计，不重复）。
- 标签/工作台/分类的增删**不在本轮**（卡片历史优先）。
- 主 JSON 性能红线不受影响：事件日志独立 key，不进 `zy_data_v2`。
