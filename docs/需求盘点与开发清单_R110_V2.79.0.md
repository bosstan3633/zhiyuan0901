## 二、Bug 定性与修复方案

### BUG-1 · 资源台「⚠ 镜像 1 条待清理」

**根因（实锤）**：资源台指标格文案来自 `curationMetrics().mirrored`，经 `isMirrorView(r)`（`'__mirrorProjId' in r`）判镜像。单向挂载红线下**不可能有投射指向资源台**（R75 注释自证：「镜像数>0 只可能是历史脏数据」）——即资源台里有一张卡的原始数据被持久化了 `__mirrorProjId` 视图模型标记（视图模型属性泄漏进 storage 的脏数据）。

**修复三步**：
1. **净化**：启动期（repository loadData 归一化段）一次性剥离资源台卡上残留的 `__mirrorProjId`/`__mirrorCat` 等视图模型标记；同时核查 `curationProjections` 是否有 wsId 指向资源台的投射记录，有则一并清除（回归断言守护）；
2. **兜底**：`curationMetrics` 对 hub 台（`isHubWs`）镜像计数恒 0（红线语义，不再依赖数据干净）；
3. 提示格回退正常「分类 N · 待分类 M」。

### BUG-2 · 附件明细点击不跳卡 / 「卡片不存在」

**现状**：`openDrillAsset` 只做附件本体预览/打开，从不跳卡；部分明细行的来源是外部 URL 标题（孤儿附件——卡已不在，附件本体/元数据残留）。

**修复（按用户建议逻辑）**：
1. `attachmentItems` 构建时标注 `cardExists`（卡存在且未软删）；
2. **卡存在**：点击行 → 关抽屉 + 跳转定位到卡片（资源台 `/workspace/<id>?hl=<cardId>`；卡在策展台则 `/curation?hl=<cardId>`）；
3. **卡不存在（孤儿）**：行内常驻 🗑「清理」按钮——二次确认后从 IndexedDB 删附件本体 + 摘除残留引用 + 行即时消失；顶部提供「🧹 清理全部孤儿附件」批量入口（确认框报数）。

### FS · 金字塔全屏技术调研（结论：**可行，0.5 天**）

**现状**：金字塔视图已存在于资源台与策展台（同一 `Workspace.vue` 内 `viewMode==='pyramid'`，根节点=论点）。

**两条路线对比**：

| 路线 | 实现 | ESC | 卡片点击 | 风险 |
|---|---|---|---|---|
| **A. Fullscreen API（推荐）** | `pyWrapRef.requestFullscreen()` 元素级真全屏 | 浏览器**原生 ESC 退出**（监听 `fullscreenchange` 同步状态） | 全屏的是 Vue 子树，点击卡片开详情**天然可用** | 新标签页非 iframe，无 allowfullscreen 限制；极老浏览器需兜底 |
| B. CSS fixed 覆盖层 | position:fixed inset:0 + 提升 z-index 复用同一组件 | 手动监听 ESC | 同样可用 | 与 topbar 层级/滚动锁定需手工处理 |

**结论**：路线 A 为主、路线 B 自动降级（`requestFullscreen` 不存在或 reject 时切 fixed 覆盖层）；两台共用一次实现；全屏内卡片详情交互由既有抽屉/弹窗天然承担；另加显式「⛶ 退出全屏」按钮双保险。**预估 0.5 天。**
