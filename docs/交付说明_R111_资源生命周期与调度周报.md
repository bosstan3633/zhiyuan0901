## 二、BUG-1 · 资源台镜像脏数据净化

**用户现象**：资源台卡片总数格常驻「⚠ 镜像 1 条待清理」——资源台本不该有任何镜像。

**根因（实锤）**：单向挂载红线下投射只能是「资源台 → 策展台」，不可能有投射指向资源台
（R75 注释自证：镜像数 > 0 只可能是历史脏数据）。实际是**视图模型标记被误持久化**：
`boardCardsOf` 给镜像卡浅拷贝打的 `__mirrorProjId` 标记，经由某条写路径落进了 storage。

**三步修复（三层防御）**：

1. **净化**：`hub.ts` 新增 `scrubHubMirrorMarkers(d)`——幂等剥离资源台卡上的
   `__mirrorProjId` / `__mirrorCat` 标记；并清除 `curationProjections` 中 `targetWsId`
   指向资源台的投射记录（历史版本未拦截）。启动期在 `loadData()` 归一化段调用一次
   （紧邻既有的 `pruneDanglingProjections`），下次 persist 固化。
2. **兜底**：`curationMetrics` 对 hub 台（`isHubWs`）**镜像计数恒 0**、全部计入 native——
   不再依赖「数据一定干净」，净化尚未落盘的那一拍也不会冒出噪声。
3. **回退**：`hubCountHint` 删除「⚠ 镜像 N 条待清理」分支，口径恒为「分类 N · 待分类 M」。

> 断言守护：R110-B1-1/2/3。R75-6、R75-8 两条旧断言按项目惯例**退役改写**（承接方已标注）。

## 三、BUG-2 · 附件明细跳卡 + 孤儿附件清理

**用户现象**：附件明细里点某一行没有反应（此前只做「预览 / 打开」，从不跳卡）；
「来自：XXX」的来源卡其实早已不在，附件本体与元数据成了孤儿，没有任何清理入口。

**修复**（`CurationDrillDrawer.vue` + `Workspace.vue` 双侧）：

- **行三态判定**：`ok`（正常）/ `missing`（本体缺失——卡还在但 IndexedDB 里附件没了）/
  `orphan`（来源卡已不存在）。判定依据两路：宿主传 `cardExists(id)`（跨台全量、含未软删条件）
  + 抽屉打开时对 IndexedDB 做一次**只读** `getAllAssetIds()` 扫描（未就绪时不做本体缺失判定，
  避免误标）。
- **点击行 = 定位来源卡**（主诉修复）：关抽屉 → 卡在本台就地高亮 + 滚动居中；卡在别的台则
  路由 `/workspace/<wsId>?hl=<cardId>`（复用 R48 A-2 既有 hl 链路）。异常行改为**提示怎么清理**，
  不再静默无反应。
- **预览能力不丢**：行尾 👁 按钮保留原有「图片行内预览 / HTML·PDF 新标签」行为。
- **清理双入口，均二次确认**：
  - 行内 🗑：`missing` 摘除卡片上的失效引用；`orphan` 删本地残留本体；
  - 顶部「🧹 清理全部孤儿附件」批量条：报数后一次清理（**复用 REQ-048 `cleanupOrphanAssets` 语义**——
    keep 集是「全部卡片（**含回收站软删卡**）的附件并集」，软删可恢复故其附件必须保留）；
  - 抽屉另列一段「🧹 孤儿附件本体（N）」逐条可删（本体在本地但无任何卡片引用）。

> 断言守护：R110-B2-1~4（B2-4 专门守护「回收站卡附件必须保留」这条红线）。

## 四、LC · 资源生命周期

### 4.1 引擎（`shared/utils/lifecycle.ts`，纯计算零写入）

| 状态 | 判据 |
|---|---|
| 🔥 活跃 | 30 天内有活动，**或**创建不足 14 天（新卡宽限） |
| 🧊 冷却 | 超过 30 天没有活动 |
| 📦 归档 | 超过 90 天没有活动，**或**用户手动 `lifecycleArchived = true` |

- 判定基准：资源卡 / 好奇心卡 = `lastCalledAt ?? updatedAt`；任务卡 = `completedAt ?? updatedAt`，
  **进行中（doing）的任务恒活跃**。
- 阈值固定 30 / 90 天，**不做设置页配置**（04-58 拍板项 1：少一个要调的旋钮）。
- 三卡泛化（资源卡 / 好奇心卡 / 任务卡）；**策展台镜像卡跟随源卡状态**，不单独计时
  （拍板项 3）——故资源台面板只列本台原生卡。

### 4.2 面板（`LifecyclePanel.vue`）

甜甜圈三态 + 三态数字（**点击数字切换下方列表**，即下钻）+ 条目显示「已闲置 N 天」；
冷却项可「📦 归档」/「忽略 30d」；归档区可「🔥 重新激活」；点击条目 → 关面板并定位。

**⚠ 本轮修掉的一处设计缺陷（重要）**：面板原实现是「直接改传入的卡对象 + emit('changed')」。
若宿主把卡片 `map` 成副本传入（早先 `.lc-wire.cjs` 的接法就是这么写的），面板写
`lifecycleArchived` 只会改到副本上，`persist()` 落空——**表现为「点了归档没反应」**。
本轮改为 **面板只发意图（`archive`/`snooze`/`reactivate`）、宿主对真实 store 卡对象落库**，
三个宿主统一走新增的 `composables/useLifecycle.ts`（单点实现，避免三份复制粘贴）。
断言 R110-LC-3 专门守护这条。

### 4.4 T3 归档集成（拍板项 2）

- 归档卡从**默认视图**消失：资源台/策展台卡片列表、好奇心三视图、任务三视图全部排除归档。
- 底部一行**降级提示**：`📦 另有 N 张已归档卡片未显示（点此在 ⏳ 生命周期中查看 / 恢复）`

  只有「默认视图列表与搜索结果」排除——避免数字与卡片对不上时的二次困惑。

## 五、FS · 金字塔视图全屏

04-58 的技术调研结论「可行，0.5 天」本轮落地，**两条路线都实现**：

- **路线 A（主）**：`pyWrapRef.requestFullscreen()` 元素级真全屏，ESC 由浏览器原生接管，
  监听 `fullscreenchange` 同步组件状态；元素级全屏的是 Vue 子树，**全屏内点卡片开详情天然可用**。
- **路线 B（自动降级）**：`requestFullscreen` 不存在或被 reject（老浏览器 / 策略拒绝）→
  切 `.py-fs-fallback`（`position: fixed; inset: 0`）覆盖层，自行监听 ESC 退出。
- **双保险**：金字塔右上角常驻「⛶ 全屏 / ⛶ 退出全屏」按钮；切走金字塔视图或切台时自动退出
  （否则全屏元素被 `v-if` 卸载会在浏览器层残留黑屏）。
- 全屏态补 `:fullscreen { background: var(--bg) }` + 内边距与滚动（否则顶层的默认背景会很突兀）。

> 断言守护：R110-FS-1（路线 A + 原生 ESC）、R110-FS-2（路线 B + ESC 兜底 + 显式退出按钮）。

## 八、踩坑记录（供下一轮复用）

1. **Vue 模板里不能写 TS 断言**：`(e.card as { status?: string }).status` 会让 `vue-tsc` 直接报
   `TS1109 / TS1005`。模板里需要窄化时，写成 script 里的普通函数（本轮 `isDone(card)`）。
2. **computed 里写 ref 是自触发**：`LifecyclePanel` 原来在 `entries` computed 里
   `now.value = Date.now()`——computed 求值中改自己的依赖，属于隐患。改为在 computed 内取局部
   `const now = Date.now()`，纯计算。
3. **`.lc-wire.cjs` 等整批补丁脚本不能盲跑**：脚本里的锚串会随源码漂移（本轮至少 3 处锚点已失效：
   `import { uid } from '../utils'`、`📦 导出工作台数据`、`const highlightId` 的位置），
   且部分脚本只做了宿主半边（BUG-2 的抽屉侧完全没写）。**正确姿势：脚本当参考、改动逐处手写并核验。**
4. **传副本 ⇒ 写不回去**：面板类组件若接收映射副本又直接改 props，一定丢写。见 §4.2。
5. **E2E 脚本「中断」比「失败」更危险**：`e2e.cjs` 最后更新停在 **R69（V2.38.1），已 40 轮未动**，
   而 R72/R73「资源台收敛」就把 `#/curation` 改成了 redirect。E2E-5 的 `dblclick` 超时抛出**未捕获
   异常**终止脚本 → 其后 13 条断言（含 E2E-10/18 两条架构级失效项）**从此从未被执行**，红灯一直没
   被点亮。本轮修好中断点后，4 条历史漂移才首次暴露。**教训：修好中断点必须全量复跑，别只看前几条。**
6. **同文件多行替换用「内容定位」而非行号**：本文件（e2e.cjs）上 grep 报的行号与 `split(/\r?\n/)`
   的数组索引会差 1。临时补丁脚本改为「唯一子串 `findIndex` + 替换前校验首尾行」，避免错切整段。
7. **行尾会污染 diff**：Edit 工具在 Windows 检出下可能写入 CRLF；一旦用 `split(/\r?\n/)` 再 `join`，
   整文件行尾会被统一改写（本次 e2e.cjs 一度 538 行 LF → 558 行 CRLF）。改完必须复核
   `grep -qU $'\r' <file>`，并归一化回 LF（本仓 `core.autocrlf=true`，LF 提交后仍会以 CRLF 检出）。
8. **headless 下 `dblclick` 会被 hover 才出现的动作条拦截**：Playwright 先 hover 再按元素**中心**取点，
   而资源卡右上角 `.rc-action` 恰好只在 hover 时出现 → `TimeoutError`。解法：取 `boundingBox` 后用
   `page.mouse.dblclick` 点**左下角内边距**，并保留 `dispatchEvent('dblclick')` 兜底。

| M6 全局搜索浮层唤起 | 3.4ms | 4.8ms | 8.9ms |

**结论**：
1. **性能回归的主体在 R72~R109 之间累积（38 轮），不是 R110/R111 引入** —— 本轮在 M4a / M4b / M3 上
   反而**显著改善**（-61% / -67% / -54%）。
2. 但 **M1 冷启动与 M2a 切台在本轮变差**（941→1831ms / 1144→1865ms），须在校准轮单独复核。
3. **根因（与 E2E 同构）**：`scripts/perf.cjs` 自 **R71** 建立后，`docs/` 内**再无第二份含 perf 数据的
   交付说明** —— 门禁 40 轮未运行，回归无人观测。
4. 以上为**单次采样**，正式基线须按 R71 纪律（预热 2 次 + 5 次取中位数）重新校准；
   `M2b 切到策展台` 在 R109 与 R111 同为 15006ms，疑为脚本内超时上限。
