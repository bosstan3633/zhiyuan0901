# 交付说明 · R71（V2.40.0）结构性性能治理

**发版日期**：2026-09-11 ｜ **版本**：V2.40.0 ｜ **基线**：V2.39.0（96c79f8 → 本轮待 commit）

> 本轮为**性能版**：**零界面改动、零交互改动、零数据模型改动、零存储格式改动**。只做一件事——把"打开就顺"从愿望变成可复现、可回归的硬指标。所有优化均在保持对外行为完全一致的前提下完成，用户不需要迁移任何数据。

## 一、为什么这一轮是性能

产品把「5 秒入台 / 3 秒调出」写进定位，**"快"本身就是卖点**。但随着资源台归一（760 张卡量级）、策展台金字塔与镜像投射叠加，两个视图的渲染路径里积累了三类结构性反模式：

| 反模式 | 具体表现 | 复杂度 |
|---|---|---|
| 分类树每次调用全表扫描 | `cats.find(c => c.id === pid)` / `cats.filter(c => c.parentId === pid)` 在**递归函数与模板表达式**里反复调用（侧栏单节点即 5 次） | 整树渲染 **O(n²)** |
| 模板内方法调用 | 卡面路径徽标 / 分类聚合计数 / 看板列分组在模板里逐卡调用，每次重渲染全量重算 | O(卡片数 × 分类数) |
| 长列表全量参与布局绘制 | 760 行列表一次性进入布局与绘制 | O(可见 + 屏外) |

## 二、交付内容

### P0 建立可信的性能基准测试台（先测量，再优化）

新增 `v2/scripts/perf.cjs`：以 playwright-core 加载**真实 dist 扩展**，种入可控规模的合成数据，在真实渲染管线里测量主线程工作量。

- **规模档**：small / medium / large；本轮结论以 medium 为准（资源台 100 分类 / 760 卡片 / 402 投射 / 400 任务 / 6 策展台 / 20 台内分类）。
- **指标体系**：M1 冷启动可交互、M2 切台（顶栏 → 视图就位端到端）、M2b 侧栏重渲染、M2c/M4b 搜索键入 6 字、M3 交互期长任务、M6 全局搜索浮层唤起、以及各视图（卡片 / 列表 / 看板 / 金字塔）切换明细。
- **测量纪律**（避免自欺）：① **JIT 预热 2 次不计入**，正式采样 5 次取**中位数**；② 只计**主线程工作**（`__flush` 排空微任务即停），**剔除 16.7ms 帧等待**——否则帧等待会把卡顿稀释掉；③ 冷启动测量前先 `goto('about:blank')`，确保是**真冷启动**（否则 `page.goto` 只改 hash 不重载文档）。
- **A/B 方法**：`git stash` 回退 `v2/src` → 构建基线 dist → 测 2 轮 → `stash pop` → 构建优化版 → 测 2 轮 → 取中位数对比（脚本 `.workbuddy/tmp/ab_r71.sh`）。

> **过程纠错（值得留档）**：首轮测试出现「切到策展台 = 15007ms」的假象。根因是顶栏策展台 Tab 的**显示文本**是 `icon + name.replace(/^[^\s]+\s/, '')`——会剥掉名字里第一个空格前的 token，所以 `name="策展台 0"` 在 Tab 上只显示「0」，按名字匹配永远选不中。修正为按**可稳定匹配的种数据命名**导航后，全部指标回归正常。**测量脚本本身也要被验证**——这是本轮的第一条教训。

### P1 分类树索引层：一次建表，处处 O(1)

新增 `v2/src/shared/utils/catIndex.ts`（165 行）：

- `buildCatIndex<T>(cats)` 返回 `{ byId, childrenOf, roots, childCount, hasChildren, descendants, family, depthOf, pathOf }`——一次 O(n) 遍历建表，`descendants / family / depthOf / pathOf` **结果缓存**（同一棵树内只算一次）。
- **防环口径与 `sanitizeCategoryTree` 完全一致**：DFS 与沿父链上行均带 `visited`；孤儿 / 自引用节点视为根节点。**R70 撒在各视图里的防环逻辑，本轮统一收敛到索引层**。
- `buildBucketIndex<T>(items, keyOf)`：把卡片按分类一次分桶成 `Map<string, T[]>`，替代反复 `filter` 全量卡。

**两视图总收益**：`Workspace.vue` **25 处**、`CurationCenter.vue` **12 处**查找/递归/模板调用重写为索引查表。

| 落点 | 改前 | 改后 |
|---|---|---|
| `childCatsOf` / `rootCats` / `descendantIds` / `familyIds` / `catAggCount` | 每次全表 `filter` | `catIdx` 查表 |
| `catNameOf` / `catIconOf` / **`catNameOfFamily`（卡面路径徽标）** | 沿父链反复全表 `find`，O(深度×n)，且模板里逐卡调用 | `catIdx.pathOf` + `byId` |
| `levelOf` / `subtreeHeight` / `deepDescendantIds` / `nodeCount` | 递归 + 模板内调用 | 预计算 `nodeCountMap` / `catHeightMap`，模板调用签名不变 |
| `cardsIn` / `projCardsIn` / `liveCardsOfCat` / `resourcesByCategory` | 每次 `filter` 全量 | `nativeBucket` / `projBucket` / `liveSrcBucket` / `resBucket` |
| 侧栏 `SidebarCat` | 模板内 `hasChildren()` / `catAggCount()` / 计数三连算 | **预计算** `hasChildren / aggCount / directCount` 三字段 |
| 看板列 | 每列各调一次分组函数 | `kanbanColumns` 预计算 |

### P2 数据聚合层：单遍化与 id 索引

- **`hub.ts boardCardsOf`**：由「每条投射都 `d.resources.find`」的 **O(投射 × 资源)** 改为先建 `byId` Map 的 **O(投射 + 资源)**。此函数是策展台每次重渲染的根 computed（`allResources` / `curationMetrics` 都调它），收益被放大。
- **`hub.ts curationMetrics`**：主题卡判定 / 原生-镜像计数 / 附件清单 / 最近更新 / **分类卡数分布**合并为**一次遍历**；「空节点」判定由嵌套 `filter × some`（O(分类 × 卡)）改为 `hasChild` Set 查询（O(分类 + 卡)）。

### P3 持久化与事件日志：去掉重复做功

- **`repository.ts saveData / saveDataNow`**：原实现 `JSON.stringify(JSON.parse(JSON.stringify(cache)))` 是**整树 2 次序列化 + 1 次多余解析**；因 `stringify(parse(X)) ≡ X`（键序由插入序保持），中间往返纯属冗余。现改为**一次 `stringify` 得到"存储实际内容"**（同时充当自身写入指纹），再 `parse` 同一串得到纯净 plain 树——**语义完全等价**（reactive Proxy → plain JSON 的净化仍然发生），成本减半。
- **`repository.ts isSelfWrite`**：先比**长度**再比内容。非本页写入几乎都会在长度这一关短路，省掉整串逐字符比对。
- **`eventLog.ts flushCardEvents`**：本函数在**每次保存**时都执行。原先先 `collectCards(d)` 建整张中间数组（1450 张卡就是 1450 次对象分配）、再遍历它建新快照——**两趟**。现改为**就地扫描资源 / 任务 / 好奇心三个数组**，并在扫描时同步建好 `nextSnap`（一趟），`prevSnap` 保留旧引用供 diff。

> **过程纠错（第二条教训）**：把事件日志的「快照重建」改成扫描时同步建好后，`tsc` 报 `Cannot find name 'current'`——因为 diff 段仍引用已被删除的中间数组。修法：先 `const prevSnap = snapshot` 保留旧引用，扫描建 `nextSnap`，末尾 `snapshot = nextSnap`。**重构删中间变量时，先确认还有谁在引用它。**

### P3 渲染层：长列表离屏跳过

| 位置 | 类 | 处理 |
|---|---|---|
| 资源台 卡片视图 | `.cur-card` | `content-visibility: auto; contain-intrinsic-size: auto 132px` |
| 资源台 **列表视图** | `.res-row` | `content-visibility: auto; contain-intrinsic-size: auto 42px` |
| 策展台 卡片视图 | `.res-card` | 沿用 R55 |
| 策展台 列表视图 | `.res-row` | `content-visibility: auto; contain-intrinsic-size: auto 44px` |

另：策展台**下钻面板惰性求值**——`drillOpen === false` 时 `drillCatRows / drillNative / drillMirror / drillRecent` 直接返回空数组，抽屉未打开不做任何全量计算。

**资源台「列表」是本轮最大单点**：307.5ms → **36.9ms（-88%）**。诊断过程是——A/B 首轮发现它是唯一**未改善**的项（307 → 297ms），核对后确认它是四项长列表里唯一**没加离屏抑制**的（另外三项 R55/R71-P4 已加），补上后一举拿下。

### 关于冷启动（诚实的边界）

冷启动 **806ms 未被优化**，且**不应**被优化掉——分解显示：`dcl ≈ 70ms`、`mounted ≈ 800ms`，其中约 700ms 是 **MV3 扩展冷启 + `dist` chunk 首次加载 + 首次存储读取**，属浏览器与 IO 的固有成本，不是计算瓶颈。**如实标注边界，比虚报收益更重要**：本轮的靶点是**交互期的计算与渲染**，冷启动不在其中。
