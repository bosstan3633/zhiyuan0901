## 〇、现状勘察结论（决定拆解方案的关键发现）

### 发现 1（REQ-030 根因）：撤销失效 = 对象引用被 onChanged 替换
- 删除流程现状：`r.deletedAt = Date.now()` + persist（防抖 300ms 写 storage）→ Toast「撤销」回调 `r.deletedAt = undefined`。
- **根因**：`stores/app.ts` 注册了 `chrome.storage.onChanged` 监听（含**本页面自身写入**）。persist 写入后 onChanged 触发 → `syncCache(newData)` + `data.value = newData`——storage 读回的 `newValue` 是**全新对象树**。
- 删除时闭包捕获的 `r` 是**旧对象引用**；用户点撤销时修改旧引用，对当前数据树无任何影响 → **撤销必然失效**。三类卡（Workspace 单删/抽屉删/批量删、CuriosityPanel、CompassActions 单删/批量删）全部中招，与反馈一致。
- **修复要点**：撤销回调一律改为**按 id 从当前数据树查找**后再清除 `deletedAt`（`d.value.resources.find(x => x.id === id)`）。

### 发现 2（REQ-027/028 可复用资产）
- 看板视图已实现"按分类分列 + 跨列拖拽=改分类归属"（`kanbanCategories` / `onDropToCategory`，第廿八轮），**分组分区可复用其分类归组逻辑**。
- 分类树已有二级结构（`Category.parentId`，最多 2 级）+ `familyIds` 聚合工具 + `catIconOf/catNameOfFamily` 徽标工具 + `marksort.ts` 标记权重排序。
- 卡片/列表视图现状：**全局「置顶区 / 非置顶区」两分区**，非置顶区标题即当前分类——需按 REQ-027 重构为按分类分区。

### 发现 3（REQ-029）与 Toast 现状
- `CompassShell.vue:82` 的 `side-note` 三行常驻文案待移除；三个入口 `cat-item` 已具备点击导航，无 hover tooltip、无首次引导。
- Toast 存在**三套实现**：`shared/components/Toast.vue`（5s/2.5s）、Workspace 内建 toast（5s/2s）、GlobalPopups 全局弹层（不同签名）。REQ-030 要求统一 3 秒语义，建议收敛。

## 五、REQ-031 · 系统性能调优（全局检索 / 快速采集 / 定位卡片 丝滑化）

> 来源：用户本轮新增需求——「全局检索、快速采集、定位卡片等交互要提升响应速度，更加丝滑」。

### 性能勘察结论（瓶颈清单，全部已定位）

| # | 瓶颈 | 位置 | 量级评估 |
|---|---|---|---|
| P-031-1 | **搜索关联 O(n²) 查找**：每张资源卡都 `workspaces.find` + `categories.find`；任务卡项目名是**嵌套双循环** `for dir { for p }`；工作台条目每台一次全量 `resources.filter` 计数 | `search-overlay.ts collectResults` | 千卡规模每次按键 ~3 次全量数组扫描 |
| P-031-2 | **渲染二次 O(n²)**：`renderResults` 每类型组 `searchResults.filter(...)` + `items.indexOf(item)` | `search-overlay.ts renderResults` | 结果 100 条时 ~5 组 × 2 次全量遍历 |
| P-031-3 | **每次按键重建计数与 Tab DOM**：`runSearch` 每次调 `renderTypeTabs` → 4~5 次 `countByType` 全量 filter + 整行 tab 重建（类型没变也重建） | `search-overlay.ts` | 每键触发 |
| P-031-4 | **escapeHtml 用 createElement**：每个结果项调用 2~3 次，高频路径慢 ~10 倍 | `search-overlay.ts` | 结果渲染整体耗时的一部分 |
| P-031-5 | **应用内搜索无防抖**：`v-model="searchQuery"` 每键直接驱动 `filteredResources` 全量 filter + `applySort`×2 + 分区 computed | `Workspace.vue` | 快速键入卡顿帧 |
| P-031-6 | **persist 后整页重渲染**：`chrome.storage.onChanged` 含**本页面自身写入**，每次保存都 `syncCache` + `data.value = newData` 全树替换（storage 读回 = 新对象树）→ 全部依赖 data 的 computed 失效重算 | `stores/app.ts` + `repository.ts` | 每次保存一次全页重算（REQ-030 同源问题，此为其性能面） |
| P-031-7 | **定位串行等待**：`handleLocate` 对每个已开新标签页**串行** `askRoute`（600ms 超时），N 个标签页最坏 N×600ms 才命中 | `background/index.ts` | 多标签页下定位明显延迟 |
| P-031-8 | **采集去重全量扫描**：`saveCapture` 保存时 `resources.find` 全量 + 每张卡 `normalizeUrl` 正则处理 | `search-overlay.ts` | 千卡下保存动作耗时 |

### 功能事项

| 功能点 | 描述 | 验收要点 |
|---|---|---|
| F-031-1 | 全局检索输入到结果渲染无感知延迟（千卡规模 <50ms） | 性能面板量化：按键→结果帧 <50ms |
| F-031-2 | 快速采集保存响应迅速（千卡规模 <150ms） | 保存→「已保存」状态即时 |
| F-031-3 | 定位卡片多标签页下快速命中（<500ms） | 3 个新标签页场景实测 |
| F-031-4 | 数据保存后无整页重渲染抖动 | onChanged 自身写入跳过生效（DevTools Performance 确认无全页 re-render） |
| F-031-5 | 应用内搜索键入流畅无掉帧 | 快速连续输入无卡顿 |
