## 二、处置：取景侧等它落定，产品不动

```js
await page.evaluate(async () => {
  const settle = () => {
    window.scrollTo(0, 0)
    const de = document.scrollingElement || document.documentElement
    if (de && de.scrollTop !== 0) de.scrollTop = 0
    return window.scrollY
  }
  for (let i = 0; i < 5; i++) { if (settle() === 0) break; await new Promise(r => setTimeout(r, 60)) }
}).catch(() => {})
```

- 读回 `window.scrollY` 而不是"发完 scrollTo 就认为完了"；最多补五次、每次 60ms（正常路径第一次就返回 0，代价是一次 evaluate 往返）。
- 顺带清 `scrollingElement.scrollTop`（两处都可能留残值）。
- **落定发生在装 calm 之前**——这条顺序由判据钉住（先定住视口，再关动画，反过来就又给了一次抢时间的窗口）。
- 真落不了定也不假装没事：残值仍然留在 `scene-state.json` 里，红的时候 `--why` 会照样把它打出来。

**复测**：修后再跑 3 份全量跑、两两 3 对成对判 ⇒ `st-manual` **三对全 0 差**。
★样本量如实：修前 6 对里中 3 对、修后 3 对里 0 中。这不是一次"碰巧没碰上"——机制是被点名的（`scrollY 0.5` 直接写在证据行里），但 0.5px 残值的**上游**（谁在滚、为什么停在半像素）我没往产品侧追，因为取景侧等落定就根治了，而那属于 #127 的原始问题（截图可比性），不是用户可见的缺陷。
