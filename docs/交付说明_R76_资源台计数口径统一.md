## 一、为什么：三个真实缺陷

R3 原文写的是"四处同口径"。动手前把资源台**所有**出现计数的地方做了一次全量勘验（不信注释，只读源码），得到八处、三种口径：

| # | 位置 | 现口径 |
|---|---|---|
| 1 | 左树「全部」 | 全台可见卡（含镜像） |
| 2 | 左树「待分类」 `:818` | **严格**：`!r.categoryId` |
| 3 | 左树命名分类 `:189` | **混用**：`hasChildren ? aggCount : directCount` |
| 4 | 看板列 `:1074` | **直属** |
| 5 | 卡片/列表分组 `:1036` | **直属**；待分类组用**宽松** |
| 6 | 下钻抽屉待分类行 `:777` | **宽松** |
| 7 | 卡面「所在分类」 `:1479` | **宽松** |
| 8 | R18 指标条 hint | **严格** |

由此定位三个缺陷：

**D1 · 待分类三口径（功能性缺陷）**
`categoryId` 指向已删/不存在分类的**悬空卡**：卡面 `:1479` 把它显示为"待分类"，下钻 `:777` 和卡片分组 `:1024` 也把它算进待分类，**但左树 `:818` 与指标条不认它**。后果是——**卡上写着「待分类」，点左树「待分类」却找不到这张卡**。这不是口味问题，是缺陷。

**D2 · 左树内部聚合/直属混用**
`:189` 的三元表达式让同一棵树里有子节点的显示聚合数、叶子显示直属数。父子数字**不可加**：父 5（含子 2）+ 子 2 = 7，实际只有 5 张。

**D3 · 同一节点同屏两个数（最关键）**
左树与卡片区**同屏可见**。分类 A 直属 3 张、子分类 B 有 2 张时：左树 A 显示 **5**（聚合），右侧卡片区组头显示 `📁 A · 3`。用户在**一屏之内**看到同一个 A 有两个数字。

## 二、方向判定：统一为「直属」，不是「聚合」

R3 原文"命名分类 `title` 注明'含子分类'"容易被读成"改用聚合口径"。**但 D3 证明聚合不可行**：

- 看板列与卡片/列表分组渲染的就是**直属卡**，count 必须等于组内实际卡片数才自洽；
- 若左树改聚合，就与看板列、卡片分组**处处打架**；
- 若把看板列/卡片分组也改聚合，则子孙分类的卡会**重复出现**在父列和自己列里，且摧毁看板"每个分类一列"的结构；
- 只有**统一为直属**能让等式成立：
  `A(3) + B(2) + C(3) + 待分类(2) = 10 = 全部(10)` ✓
  ——全表自洽、数字可加总、同屏无冲突。

**"含子分类"仍然注明了**，只是含义改为提示口径与子分类规模：父节点 hover 显示
「仅本分类直属 N 张 · 含 M 个子分类（共 K 张）」——聚合信息不丢失，但不再作为显示值制造歧义。`aggCount` 不浪费，转作 title 里的"共 K 张"。

> ⚠ 该方向判定需产品负责人确认；若坚持聚合，需连带改看板列与卡片分组的**渲染内容**，属 R3 之外的范围。

## 三、交付内容

### 3.1 待分类判据收敛为唯一实现 `isUncat`

```ts
/** R76（R3）：待分类判据——无分类，**或**分类已失效（categoryId 指向本台不存在的分类）。 */
function isUncat(r: ResourceCard, validIds: { has(id: string): boolean }): boolean {
  return !r.categoryId || !validIds.has(r.categoryId)
}
```

签名只依赖 `has`，故 `catIdx.byId`（Map）与自建 id Set 都能传入。五处调用点全部改为消费它：

| 卡片/列表分组 | `!r.categoryId \|\| !validIds.has(...)` | `isUncat`（等价改写） |
| 下钻抽屉待分类行 | 同上 | `isUncat`（等价改写） |
| 卡面「所在分类」 | 同上 | `isUncat`（等价改写） |

## 四、一处历史断言修正

回归首次跑出 **1 失败**：`R71-4`（策展台侧栏预计算）。原因是该断言按**接口字段连串**匹配：

```js
w.includes('hasChildren: boolean; aggCount: number; directCount: number')
```

新增 `childCount` 后字段序列被截断。这是**断言过严，不是实现问题**（R71-4 的意图是"三个字段在 computed 里预计算、模板不再递归"）。已改为**分字段匹配**（字段名与预计算赋值各验一次），容忍字段顺序变化与新增：

```js
return w.includes('hasChildren: boolean') && w.includes('aggCount: number') && w.includes('directCount: number')
  && w.includes('hasChildren: catIdx.value.hasChildren(c.id)')
  && w.includes('directCount: (resBucket.value.get(c.id) || []).length');
```

**断言名称冻结未改**（项目惯例），只改断言体。
