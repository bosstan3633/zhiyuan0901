## 一、基类外提：修掉一整轮被假绿掩盖的真实回归

### 1.1 结论先行

上一轮（`170124b`）报「像素 A/B 三个子域 0 差 / 纯结构重构的硬证据」。

### 1.2 证据链（三步，每步都独立可复现）

**第一步 · 目视**：打开上轮的实拍图，`settings-linear-manual.png` 是一张**没有任何卡片外壳**的空白页
（只有一枚图标、两行字、一个按钮浮在纯背景上）。同目录未拆的 `settings-linear-resource.png`
卡片边框、圆角、卡影齐全。⇒ 拆出去的子域样式掉了。

**第二步 · 计算样式**（`v2/scripts/probe-gs-baseline.cjs`，新增量具）：直接读 `getComputedStyle` 与 `data-v`：

| 选择器 | 已拆子域（manual/about/letter） | 未拆宿主（resource） |
|---|---|---|
| `.gs-card` | border `0px` · radius `0` · bg `rgba(0,0,0,0)` · shadow `none` | `1px` · `14px` · `rgb(20,22,27)` · 有卡影 |
| `.gs-page-title` | `13px / 400` | `17px / 700` |

`data-v` 直接给出病根：子组件内部元素只带 `data-v-97a6a3d8`（自己的），
而宿主的规则编译成 `.gs-card[data-v-a193e574]` ⇒ **不匹配**。

> **Vue 的 `scoped` 是按组件实例给元素打标记，父组件样式命中不了子组件内部元素。**
> 所以这不是"某几条 CSS 漏搬"，而是**每拆一个子域就会重演一次**的系统性陷阱。

**第三步 · 为什么像素 A/B 没抓到**：那条 A/B 的新旧两张图是同一张。
交付说明第四节自己记着这个失败模式（「修好导航路径后等就条件仍按旧 hash 判 ⇒ 跳过 0 张
⇒ img-diff 报逐像素一致」），但它被当成**已修好的历史问题**记下了，
而那句「0 差」的结论是**修好之前**那次跑的产物，此后没再真跑。
⇒ 假信号套着假信号，还套着一个"已修复"的自我安慰。

## 二、判据：把"注释里的约定"变成可执行守卫

### 2.1 为什么不用像素量具

像素量具贵、且会被"跳过 0 张"这类假信号吃掉（1.2 已实证）。
而这次病根是**纯结构性的**——某组件用了基类却没引基类表。这类事实静态判据就能查，且查不漏。

### 2.2 新分片 `33-gs-baseline.cjs`（5 条）

| 判据 | 锁什么 |
|---|---|
| `P0-S8` | 基类表存在、非空壳（≥20 条选择器）、真含 `.gs-card` / `.gs-btn` |
| `P0-S8b` | 宿主骨架类不得误入基类表 |
| `P0-S8c` | 宿主真引用了表，**且自带反向注入自检**（判据对锚点不敏感时自己判红） |
| `P0-S11` | **正锚**：用了 `.gs-card/.gs-btn/.gs-panel/.gs-page-*` 的组件必须引表（覆盖 `settings/` 子域 + `components/` 卡片组件）—— 这就是复发路径守卫 |
| `P0-S11b` | 表里的类不能整表零命中（防搬空 / 改错名字） |

### 2.3 反向注入自证（两条都实证过）

1. 删掉 `SettingsManualPanel` 的 `<style src>` ⇒ `P0-S11` 变红并**点名该文件**
2. 删掉整张 `base.css` ⇒ `P0-S8` + `P0-S11` 同时变红

恢复后全绿。

### 2.4 判据自己也犯了一次错（值得记）

`P0-S8b` 用 `^\.gs-page\b` 判「宿主骨架误入」，**误报了** —— 表里根本没有 `.gs-page`。
真因：`\b` 只在「单词字符 ↔ 非单词字符」处成立，而本项目类名全是 kebab-case，
`.gs-page-header` 的连字符两侧**都算非单词字符** ⇒ `\b` 落在 `-` 之前 ⇒ 假匹配。
修法：收尾改用显式字符类 `(?![a-z0-9-])`。

> ★这是纪律 21「包装对象两条路都堵死」的同族：**看着对的写法实际会塌，且塌得最有欺骗性**（报了一个不存在的缺陷）。

### 3.1 搬移脚本抓到的三个自身缺陷（都靠边界自检发现）

1. **脚本段切少 1 行** ⇒ `clearCache` 的收尾 `}` 落进下一个函数，`vue-tsc` 报两处括号不配平。
   实证修正：1519-1571 → 1519-**1572**。
2. **import 自检条件失效** ⇒ 脚本写 `if (!v2.includes('SettingsResetPanel'))` 才补 import，
   但**接线代码里刚写进模板的 `<SettingsResetPanel …>` 已经让这个条件为真** ⇒ import 永远被跳过
   ⇒ 模板引用未定义组件 ⇒ **整块不渲染**。
   症状极不直观：实拍只报「标题空、panel=false」，完全看不出是缺 import。
   修法：自检查 **import 语句本身**（`includes("import SettingsResetPanel from")`），不查组件名。
3. **正则漏了缩进容差** ⇒ `/^<div v-if=…/` 匹配不上带 6 格缩进的真实行，`findIndex` 恒 -1。

### 3.2 连带修掉一条判据的隐性顺序依赖

`R4-Dh`（`.gs-input` 必须有本体规则）原写法是裸 `indexOf('.gs-input {')`。
它命中的是 `.ai-field .gs-input { width: 100%; }` —— 那是一条复合窄化规则，**不是**本体规则。

本体规则搬进 `base.css` 后，聚合文本的先后顺序变了（复合规则在宿主、`base.css` 排其后）⇒
判据读到了那 4px 的窄化规则，于是**因为搬对了位置而判红**。

> 这条判据成立的前提从来不是「本体规则存在」，而是「本体规则恰好排在复合规则前面」——
> 一个从未被写下的顺序依赖。承重锚换成行首 `/^\.gs-input \{/m`，与 `S2-1` 同口径。

## 五、本轮新增纪律

### ★★★ 1. 像素 A/B 的结论必须自带"这次真跑了 N 张"的证据

上轮的教训不是"工具会骗人"，而是**工具骗了人之后，结论被当成已验证的事实写进了交付说明**。
⇒ 纪律：A/B 结论必须与"本轮实拍张数 / 对比张数"写在一起。
**0 张新图不是"通过"，是"没跑"**。

### ★★★ 2. 组件拆分有一个结构性陷阱：父组件 scoped 样式到不了子组件内部

`.gs-card` 这类**跨组件复用的基类**放进任一组件的 `<style scoped>`，
对其它组件一律无效（Vue 按实例打 `data-v`）。
⇒ 纪律：**凡要被两个以上组件用的样式，第一天就放全局表**，不要放进任一组件的 scoped。
判据由 `P0-S11` 守住（用了基类却没引表即红）。

### ★★ 3. 注释里写"由 X 提供"是一句需要实证的断言

`MigrateReportCard` 的注释写「非 scoped 部分由 GlobalSettings 全局表提供」——
**宿主那份一直是 scoped**。这句话把一个未验证的假设写成了"已解决"，
让同一个 bug 多活了两轮。⇒ 纪律：注释里断言"某处提供了某物"，要么 grep 实证，要么写"待验证"。

### ★★ 4. 判据里的 `includes(组件名)` 会因为模板里已有同名标签而恒真

自检条件写在**改动之后**读的文件上 ⇒ 改动本身让条件为真 ⇒ 自检静默跳过。
⇒ 纪律：自检查**动作本身**（import 语句、文件路径），不查动作的产物名。

### ★★ 5. `\b` 在 kebab-case 类名上不成立

`.gs-page\b` 会匹配 `.gs-page-header`（连字符两侧都算非单词字符）。
⇒ 纪律：类名正则的收尾用显式字符类 `(?![a-z0-9-])`，不用 `\b`。
