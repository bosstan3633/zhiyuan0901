- **版本**：V2.80.0（第 112 轮）
- **立项依据**：`文档中心/04_产品与设计/04-59_开发任务书_结构性技术债专项.md`（Q1 拍板「立即开」）

- **性质**：**纯性能与工程治理，零功能变更、零数据模型变更、零迁移**

## 〇、一句话结论

**这一轮真正的发现不是"哪里慢"，而是"我们一直在改错的东西"。**

归因（CDP CPU profile）证明瓶颈既不是拼音匹配、也不是分类树算法（R71 已做过 O(1) 索引），
而是 **「渲染规模 × 响应式读取次数」**——一次性建 400 张卡的 DOM，每张卡在模板里再调
`mountedTaskCount(r)`（O(任务数) 反向全表扫描，每卡 2 次）。修掉这两点，**搜索键入降 95%、
切资源台降 89%、长任务降 79%**（medium 档 4 次采样中位）。

同时发现 **`perf.cjs` 自 R71 建后 40 轮从未被跑过**（`docs/` 里 R71 之后无第二份含性能数据的
交付说明），且脚本自身在 R72「资源台收敛」后就已经漂移——**门禁死了，所以没人知道产品慢了**。
这与 R111 挖出的 `e2e.cjs` 停 R69 40 轮是**同一种死法**。

## 一、归因：先把热点定位到函数

### 1.1 排除法（先证伪两个"显然的"假设）

| 假设 | 证伪方式 | 结论 |
|---|---|---|
| 拼音转换拖慢搜索 | 读搜索管线：`matchCard` 是纯文本匹配，**不涉及拼音** | ✗ 排除 |
| 分类树计数 O(n²) | 读 `catIdx`：R71 已建 O(1) 查表索引 | ✗ 排除 |

**教训**：性能专项最忌「看着像就改」。两个最像的假设都不成立。

### 1.2 CPU profile 定位（`.perf-profile.json`）

热点几乎全部落在同一个压缩 chunk 的同一行，函数名为 `track` / `get` / `includes` /
`setAccessLevel` —— 这是 **Vue 响应式系统的代理陷阱**（`track()` = 依赖收集）。

| 热点 | 搜索窗口占比 | 树重渲染窗口 | 切台窗口 |
|---|---:|---:|---:|
| `it`（= Vue `track()`） | **20.7%** | **19.3%** | **10.1%** |
| `get`（Proxy 读取陷阱） | 9.6% | — | — |
| `includes`（has 陷阱） | 2.0% | — | — |
| `insertBefore` / `createElement` / `setElementText` | ≈5% | — | — |

**结论**：不是算法复杂度问题，是**规模 × 次数**问题。

### 1.3 改动前 vs 改动后（同一诊断脚本，同口径）

| 场景 | 改动前 wall / 长任务 | 改动后 wall / 长任务 |
|---|---|---|
| 切到资源台 | 4584ms / [3057, 740, 151] | **1101ms / [222, 440, 133]** |
| 搜索键入 | 37327ms / 8 个（最大 8106） | **641ms / [553, 51]** |
| 树重渲染 | 14305ms / [6193, 55, 6625] | **216ms / 无长任务** |

## 二、改动清单（7 项 + 1 项门禁修复）

### 2.1 渲染规模：增量渲染（最大杠杆）

- 资源台 / 策展台按 `RENDER_STEP = 80` 分批挂载，底部「显示更多」按钮 + 滚到底自动续
- 一次性 DOM 从 **400 张卡 → 80 张卡**（medium 档）
- 换台 / 换视图 / 换分类 / 改检索词 / 改排序时**回落**到首屏份额（避免切换后残留大批量）
- 状态：`Workspace.vue`（`renderLimit` + `visibleGroups` + 滚动续载）

> **为什么不是虚拟滚动**（Q4 拍板 B）：`content-visibility: auto`（R55-F4 已有）只跳过
> 屏外卡的 layout/paint，**不跳过 Vue 建 DOM 与响应式读取**——这正是 `track()` 占 20% 的原因。
> 增量渲染等价解决这一项，且不破坏拖拽 / 分组 / 选中结构。虚拟滚动留待真有万卡库时再评估。

### 2.2 反查复杂度：`mountedTaskCount` 缓存

- 原实现：`d.tasks.filter(t => !t.deletedAt && t.mountedResourceIds.includes(r.id))` —— **每卡 O(任务数)**
- 模板每卡调 **2 次** → 400 卡 × 2 × 400 任务 ≈ **32 万次比较，且每次重渲染都跑**
- 改为：按任务集惰性构建 `Map<resId, count>`，**O(1) 命中**
- 文件：`newtab/composables/useWorkspaceBatch.ts`

### 2.3 日期格式化记忆化

- `fieldValue` 的 `createdAt` 分支原本**逐卡**执行 `new Date(...).toLocaleDateString('zh-CN')`
  （内部构造 `Intl.DateTimeFormat`，是已知的重量级对象）
- 改为记忆化 `fmtDateCN(ts)`：同一天只算一次
- 文件：`shared/utils/fields.ts`

### 2.4 家族过滤改 Set.has

- `applyViewFilters` 的分类分支：`ids.includes(r.categoryId)` → **`Set.has`**
- 复杂度 `O(卡数 × 家族规模)` → `O(卡数)`
- 文件：`newtab/views/Workspace.vue`

### 2.5 切台零重算（KeepAlive 隐藏期空转）

- `workspaceId = computed(() => route.params.id)` 是**几乎全部 computed 的根依赖**
- 切到调度台时它变 `undefined` → KeepAlive 缓存中的 Workspace 在**隐藏期间**仍被触发一次全量重算，
  切回再算一遍 → **每次切台白做两遍**
- 改为：离开 `/workspace` 时保持上一个台 id（`lastWsId`）—— 隐藏期不再触发根依赖变更
- 文件：`newtab/views/Workspace.vue`

### 2.6 切台热度落盘节流

- 原实现：每次切台立即 `store.persist()` → 300ms 防抖后同步执行**整树 `JSON.stringify` + `parse`**
  （medium 规模 ~800 卡 / 100 分类）
- 改为：**4s 合并落盘** + 页面隐藏（`visibilitychange`）/ 组件卸载时补写（避免「切台后立刻关页」丢数据）
- 文件：`newtab/views/Workspace.vue`

### 2.7 冷启动单次读取

启动链路里同一个 `STORAGE_KEY` 被**串行读了 3 次**（实测 219ms + 197ms + 229ms）：

| # | 来源 | 处理 |
|---|---|---|
| 1 | `bootDataRobust()` → `ensureBootData()` 的 V1 检测读 | 保留（首次） |
| 2 | 随后 `loadData()` 又读同一个 key | **改用首次读到的 raw 快照**（新增可选参数） |
| 3 | `bootstrap()` 里 `ensureBootData()` **被第二次调用**，又读一次 | **会话内幂等**（`bootDataDone`，失败不置位以保留重试路径） |

- **归一化一律不跳过**：`fixTags` / `fixEncoded` / `fixTagNames` 等修复段仍在 `loadData` 内无条件执行，
  预取只跳过 IO（回归 R112-13 专门守护这一点）
- 文件：`newtab/main.ts`、`shared/storage/repository.ts`

### 2.8 门禁修复：`perf.cjs` 策展台切台漂移

- `__navTo('策展台', ...)` 前缀匹配时**误命中溢出指示「≪ N」**（`title="其余 N 个策展台"`）——
  点它只展开列表、不导航 → **打满 15s 超时**
- 后果：R109 / R111 / V2.79.0 报出的 `M2b_切到策展台 = 15006~15019ms` **全是假的**（脚本超时上限）
- 修复：过滤 `tab-overflow` 类 + 改用 `PERF0` 台名精确定位 → 真实值 **37~149ms**

### 2.9 另两处重复遍历消除

| 处 | 原实现 | 改为 |
|---|---|---|
| `fieldsOf(r)`（卡片模板逐卡调用） | 每次调用都执行 `visibleFields(d.fieldConfig, 'resource'/'thesis')` | 返回**已缓存的 computed 引用**（`thesisFields` / `rFields`），逐卡零新建 |
| `curationMetrics(d, wsId)` | 内部自己再跑一遍 `boardCardsOf(d, wsId)` —— 与宿主 `allResources` 各算一遍全量遍历 | 新增第三参**复用宿主已算出的卡数组**（调用方 `Workspace.vue` 传 `allResources.value`） |

### 3.1 采样明细（V2.80.0，medium）

| 采样 | M1 | M2a | M4a | M4b | M2b 侧栏 | M3 / 次数 |
|---|---:|---:|---:|---:|---:|---:|
| #1（构建后首次） | 1040 | 196 | 84 | 74 | 44 | 8244 / 72 |
| #2（干净） | 1294 | 209 | 113 | 166 | 64 | 20363 / 150 |
| #3（干净） | 1280 | 196 | 141 | 135 | 71 | 19671 / 154 |
| #4（干净） | 1269 | 192 | 115 | 288 | 99 | 38921 / 194 |
| **中位** | **1275** | **196** | **114** | **151** | **68** | **20017 / 152** |

**读法**：

1. **M1 / M2a / M4a 的稳定性很好**（M1 三次干净采样仅 1269~1294ms，波动 ±1%）——
   这几个数字可以直接当基线用。
2. **M4b 与 M3 抖动大**（M4b 74~288ms；M3 8.2s~38.9s，**近 5 倍**）。M3 受 GC 与
   Chromium 调度影响明显，**单次采样完全不可信**——这也是本轮要求多次采样的直接原因。
3. **#1 的 M3 = 8244ms 是四次里最乐观的一次**；采用中位后为 20017ms。
   本文档早期版本曾直接引用该单次值，已回正——**这正是 `05-6` 里"引用前先确认采样次数"
   那条纪律要防的事**。

### 3.2 口径不对等的说明

`V2.79.0（专项起点）` 的一组数字来自**单次采样**。若仅看单次对比（1040ms / 196ms / 8244ms），
会高估本轮收益。**以中位数为准则收益为 −30% / −89% / −79%**。

反过来说：起点的 1865ms 与 95000ms **也可能偏悲观**。因此 §六 把「用相同采样纪律重测
V2.79.0 基线」列为后置项 3——**在补齐这一步之前，本轮的"降幅"应当被读作量级判断，而非精确值**。

### 3.3 分批次演进（单次采样，仅供回溯方向）

| 指标 | 起点 | 批 1（增量渲染等） | 批 2（切台零重算等） | 批 3（冷启动 IO） |
|---|---:|---:|---:|---:|
| M1 冷启动 | 1831 | 2113 | 1878 | **1040**¹ |
| M2a 切到资源台 | 1865 | 1939 | **80** | 196 |

| M4b 搜索键入 | 2842 | 174 | 59 | **74** |

> ¹ 本表全部为**单次采样**，只用于判断"哪一批解决了什么"，**不作为基线**。
> 其中批 3 的数字偏乐观（见 §3.1 读法 3）。

### 3.4 冷启动拆解（当前构建）

| 阶段 | 耗时 |
|---|---:|

## 五、踩坑记录

1. **性能专项必须先归因**：两个"看着最像"的假设（拼音、O(n²) 树计数）全部证伪；
   若不 profile 直接动手，会改一堆无关代码并宣称"优化完成"。
2. **门禁脚本自身漂移会伪装成"产品慢"**：`perf.cjs` 的 `15006ms` 是脚本超时上限，
   不是产品指标——**已经被当成性能数据引用过至少三轮**。门禁输出必须与脚本版本一起复核。
3. **`content-visibility: auto` ≠ 免渲染**：它只省 layout/paint，DOM 创建与响应式读取照跑。
4. **模板内的函数调用是性能负债**：`:class="f(r)"` 形式在 N 卡 × M 重渲染下会放大 M×N 倍，
   尤其是函数内部有全表扫描时（本次 `mountedTaskCount` 即为此类）。
5. **`vite build` 清空 dist 会触发沙箱批量删除守护而卡死**（>50 文件）——
   沿用项目惯例「先改名 `dist_old` 再构建」绕过；直接 `rm -rf dist` 也会被拦。
6. **单次采样会同时骗两个方向**：同一份代码，M3 四次采样在 **8.2s ~ 38.9s** 之间摆动（近 5 倍）。
   若只跑一次就宣布"长任务降 91%"，等于用运气当结论；**本文档初稿就犯过这个错，已按中位数回正**。
7. **采样期间不能跑别的任务**：本轮前 3 次采样与我自己的打包/校验命令重叠，整体被抬高
   （M2a 从 ~196ms 抬到 185~257ms 的宽幅）。**性能采样要独占机器**——这是采样纪律的一部分，
   不只是"多跑几次"。
