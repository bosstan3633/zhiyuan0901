## 一、总评

定位执行度整体健康：六层链/策展平权/三端采集/本地零依赖等核心叙事都有真实闭环支撑；性能侧经 R56 体检（2000 卡压测零 >50ms 长任务、启动/切台/保存均在预算内）无红灯。本轮发现 **2 个 P1 级问题**（一个违反产品红线、一个数据完整性缺口）、**2 个 P2**、若干 P3，以及三个与「三秒召回」核心承诺直接相关的优化机会。

## 二、确认的 Bug（按严重度）

### B1 · P1｜删除工作台 = 物理硬删，违反「删除一律软删」红线
- **证据**：`Workspace.vue → deleteWorkspace()`：`d.value.resources = d.value.resources.filter(r => r.workspaceId !== workspaceId.value)`——资源卡直接移出数组，不写 `deletedAt`；确认弹窗文案自述「此操作不可恢复」。硬性规则 #3（README/开发指南）明令「删除一律软删（回收站可恢复）」。
- **产品后果**：误删工作台 = 资产永久丢失，回收站无从恢复；且策展中心里投射/引用这些卡的位置全部变「📡 源卡已删除」悬空态。对主打「数据主权/带得走」的产品，这是信任级缺陷。
- **建议修法**：删除工作台时对全部资源卡写 `deletedAt`（回收站恢复时连卡片带归属一并还原）；分类随台删除可保留现状（分类无软删语义）。工作量小。

### B2 · P1｜跨上下文并发写「后到全量覆盖」，300ms 窗口内的改动被静默吞掉（实机复现）
- **证据（实机复现，双新标签页）**：B 页勾选三件事槽 2 → 80ms 后 A 页勾选槽 1 → 落盘结果 `s1=todo, s2=done`——**A 的改动凭空消失**。机制：`repository.ts` 外部写入到达时 `syncCache()` **整树替换**内存数据；接收页在替换前 300ms 防抖窗口内的未落盘修改随之丢失（`selfWriteAt` 只防回环，不防冲突）。
- **更大的暴露面**：不止双标签页——**新标签页 + 网页浮层**的组合同样中招（浮层采集/浮层删除是 content script 直写 storage；新标签页只要有未落盘改动就丢）。多开窗口工作是这个产品用户画像的常态（README 画像：「使用场景横跨十几个网页」）。
- **建议修法**（按成本递增）：
  1. 低成本止血：外部写入到达时若本页有未落盘脏数据（`saveTimer` 未触发），先立即 `saveDataNow()` 抢写，再 `syncCache` 后把外部数据与本页最后已知状态做**卡片级合并**（按 `id + updatedAt` LWW）；
  2. 中成本：卡片级 merge 成为常规路径（每卡有 updatedAt，天然可并）；
  3. 兜底提示：检测到覆盖发生时 Toast「已合并来自其他窗口的 N 处更改」。

### B3 · P2｜「今日」时间边界在长开页面失真
- **证据**：`CompassHome.vue:39` `todayStart` 在组件 setup 时**一次性固化**——新标签页常开跨零点后，「今日入台/移出/调出/写入记录」的统计边界停在昨天；同族：`compass.ts → northStarMetrics` memo 键 = `period + 数据版本号`，**不含日期**——跨零点后 DHI 在轨窗口/日新增等在下次数据写入前沿用旧窗口（`isWithinDays` 内部用 `Date.now()`）。
- **后果**：调度台是常驻页，跨零点失真是确定会发生的（用户上午打开页面看到的是昨天口径的「今日」）。
- **建议修法**：todayStart 改为 computed（依赖一个每分钟更新的 now ref）；northStar memo 键拼上「当日日期串」。工作量小。

### B4 · P2｜搜索命中字段两端不一致，且应用内搜不到标签
- **证据**：
  - 应用内（GlobalPopups）检索 blob = `标题 + 工作台 + 分类 + 摘要 + 链接文本`，**不含 tags**；
  - 网页浮层（overlay-impl）资源卡 blob = `标题 + 描述 + tags + 链接`（含标签），但任务卡 blob = `标题 + 描述`（无标签、无项目名）。
- **后果**：同一查询两端结果不同；「标签」作为一级组织体系却不能在主入口被搜到（标签体系跟随导入导出刚在 R56 补齐，检索缺一角）。
- **建议修法**：抽一个共享的 `searchBlobOf(card)`（标题 + 描述 + 标签 + 分类/项目名 + 链接文本），两端同构消费。工作量小、收益直接。

### B5 · P3｜细节三则
1. 策展中心新建卡的 `curOrder = 原生卡数`，与同组投射卡已有的 curOrder 可能交错（混排网格里新卡落位偶发不在末尾）；
2. `CompassHome → projTasks` 仍用原始 filter，未消费 R56 建好的 `projectTasksOf` 共享索引（性能口径不一致，量小无感）；
3. `AppData.activityLogs` 已无任何写入方（事件日志早已迁 `zy_event_log` 独立键），属死字段，仅导入合并还在搬运它——可在迁移钩子里清空瘦身。

## 三、与定位直接相关的优化机会（价值排序）

### O1 · 搜索排序与「三秒召回」承诺的差距（核心）
- **现状**：输入查询后，结果排序 = `markRank`（置顶 2 > 星标 1 > 普通 0）稳定排序，同权重回落到**池内数组顺序**——不比热度（callCount）、不比最近调出（lastCalledAt）、不比命中位置（标题命中 vs 摘要命中）。
- **差距**：一枚早年置顶的弱相关卡永远压过昨天刚调出 8 次的强相关卡。而「调度」产品的核心心智正是「正确的时刻把对的资源召回来」——**打字态排序应该比浏览态更聪明**（浏览态反而已按热度排）。
- **建议**：同 markRank 内按「标题命中 > 其他字段命中 → callCount 降序 → lastCalledAt 降序」三级兜底；热数据（近 7 天调出）可再加权。改动收敛在两端共享的排序函数里。

### O2 · 未归档任务的「运营位」
- **现状**：快速采集三端（R55）让任务以前所未有的速度流入「未归档」池——真机截图可见 0/11、0/13 持续堆积。就地归档能力是完整的（MetricDrillDrawer 未归档清单内选项目→选指标即归档），但入口埋在顶部指标第四格。
- **建议**：任务卡库筛选器加「未归档」维度（现有 TaskFilter 只有 all/todo/doing/done）；三件事空槽态可给一条「清一清未归档任务」的轻引导。让「采集→归档」闭环的最后一厘米短一点。

### O3 · 首屏叙事的最后一环：周转率可视化
- DHI/WCE/WRR/未归档四格口径清晰，但「认知周转率」没有一个直观的**趋势**表达（全部是当期点位数）。`zy_event_log` 已有完整事件流，天然支持「近 7 天调出/新增/归档」迷你趋势条。属增强项，非缺口。

## 四、性能观察

- **健康面**：R56 打点 A/B 显示 2000 卡压测下无 >50ms 长任务；启动并行加载、拼音按需 + LRU、策展 O(n log n)、persist 300ms 防抖均工作正常；dist 1.4M 无冗余图标。
- **剩余优化空间**（均有真实触发条件，但非当下瓶颈）：
  1. **工作台超大库渲染**：`content-visibility: auto` 已兜住屏外；若单台卡数破千，卡片网格可升级虚拟滚动（现成方案成熟）；
  2. **检索倒排索引**：现策略为「每次输入全量过滤 + 拼音实时匹配」，2000 卡实测无感，5000+ 卡可预建倒排；
  3. **persist 序列化成本**：单根 JSON 全量 `JSON.parse(JSON.stringify)`，数据量到 MB 级后每 300ms 防抖写全量——可改结构性克隆或分键存储（属架构级，建议单独立项评估）；
  4. `dailyFocus`/`zy_file_paths` 等键只增不减，量级可控（KB/年），暂不必治理。

## 五、验证过、无问题的面（免重复排查）

软删全链路（卡片删除/批量删除/策展删除均写 deletedAt，回收站硬删同步清附件）；导入前自动备份 + 并集合并 + 版本校验；工作台导出同构（R56）；事件日志 5000 滚动 + 双记防护；归档闭环（未归档下钻就地归档）；DHI 三条件口径五处统一；策展混排平权与拖拽（R56/R57 根因修复后）；WRR 口径全走 `recordResourceOpen`。
