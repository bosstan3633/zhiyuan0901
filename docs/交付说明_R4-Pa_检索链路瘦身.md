## 一、开工第一步不是改代码，是发现尺子是坏的、而且量错了对象

两件事都在计划外，但都必须先做，否则 #71 的验收标准无从判起。

**① perf.cjs 起不来（本机稳定复现）。** 开跑第一件事就是
`worker.evaluate(() => chrome.runtime.getManifest().version)`，本机实测直接抛
`TypeError: Cannot read properties of undefined (reading 'getManifest')` 并在 perf.cjs:435 退出，
**一个指标都不写**。原因不是包坏、也不是扩展坏：Playwright 的 `serviceworker` 事件在**目标挂上时**就发，
而扩展的 `chrome.runtime` 绑定还要晚一拍才进上下文。同一条 evaluate 隔 1 秒再调就返回 `"3.7.1"`
（探针 `/tmp/zy_sw_probe.cjs` 实测：immediate ERR / after 1s ⇒ "3.7.1" / typeof chrome.runtime ⇒ object）。

这件事的形状和 R4-Ea 修 img-diff 一模一样：**perf 是手动跑的量具，不在回归链里，坏了没有任何一条断言会红。**
落点：`scripts/browser.cjs` 新增 `swReady(worker)`（轮询自检 `typeof chrome.runtime.getManifest === 'function'`，
默认 12×250ms，超时把 `worker.url()` 写进报错），perf.cjs 的版本回读改成
`const loadedVer = (await swReady(worker)).version`。R155 立的那三条（认 `--dist`、报告自证 build、开跑即删旧报告）
一条没松，只是"从 SW 回读版本"这句实现搬进了 browser.cjs——判据 R155-12 随之改三条腿（见第六节）。

**② #71 的验收对象此前零度量。** 任务写的是「全局检索链路瘦身」，而 perf 的 M5 和真实档 R7 量的都是
**content 浮层**（`#__zy_si__` → overlay-impl.ts），那条链的 `match()` 只做 `text.toLowerCase().includes(kw)`
——没有归一化、没有 hitRank 分级、没有五组分组、没有 v-html。#71 要瘦的是 **newtab 侧 GlobalPopups.vue**
的 `allResults → blobOf/normKey → hitResult/hitRank → groupedResults → hlTitle/v-html` 这条。
开工前在整套 perf 指标里 grep `gp-search-input` / `gp-result-item`：**零命中**。
顺手也 grep 了 e2e.cjs 与 theme-audit.cjs：**同样零命中**——也就是说 ⌘K 面板这个用户每天点几十次的东西，
只有源码文本可见，运行时零覆盖。

补的尺子（perf.cjs 新增一档，开在自己的长任务窗口 `__ltMark5c`，不污染 M3b 的跨轮可比性）：

- **M5c 应用内搜索面板唤起(ms)**：点顶栏「全局搜索」按钮 → 等 `.gp-overlay.open .gp-results` 出子元素 → `__flush()`，
  取 3 次最小值，并列写中位与窗口内阻塞。
  入口刻意走真实 UI 路径（与 perf-census R173-T2 同一条），**不在扩展页派发合成 Ctrl+K**——
  快捷键是 background commands → `zy-open-search` 消息触发的，页面里没有 keydown 监听者，
  合成按键会重演旧 M6「11.5s 墙钟里 8s 在等一个永远不会开的浮层」（R114-59 已记过一次，本次是它的应用内翻版）。
- **M5d 应用内搜索键入净耗时(ms)**：复用现成的 `__searchTypeBill`，词面 `资源条目 1`（合成库里大面积命中，
  让归一化/分组/渲染全按重档走），并展平中位/散布/阻塞/最大单任务/长任务数。
- **M5d 命中行数 / 渲染行数**：读 `.gp-group-cnt` 之和与 `.gp-result-item` 数——没有这两个数，
  "快了多少"可以被"命中的卡变少了"冒充（这是尺子自己的防伪）。
- **M3f 搜索面板窗口长任务**：整窗阻塞量与次数。

## 二、基线与归因：先量，再决定动哪一刀

合成库 `--scale=large`（资源卡 1,540 + 任务 700 + 好奇 300 + 策展台 8 + 项目 36 = 面板 tab 计数 2,548）。

| 指标 | 改前基线 | 读法 |
|---|---|---|
| M5c 唤起（3 次最小 / 中位） | **69.5 / 70 ms** | ★超 #71 验收线（唤起 <60ms） |
| M5c 窗口内阻塞 / 最大单任务 | 86 / 86 ms | 一次开面板一条 86ms 长任务 |
| M5d 键入净耗时（最小 / 中位） | 11.9 / 16.3 ms | 「<16ms 单帧」压线 |
| M5d 命中 / 渲染行数 | 801 / 30 | 尺子自证：命中没变少 |
| M3f 窗口长任务 | 205 ms / 3 次 | |

归因用 CDP Profiler @1kHz 卡在两个窗口上取**函数级 self 账单**（`/tmp/zy_pa_attr.cjs`，种子库与 perf 同构）：

- **唤起**：满库连开 5 次 81/100/97/100/102ms，**不衰减** ⇒ 每次开面板都在重付出；
  而 JS 采样极小（`focus` 20、`(program)` 10，其余个位数）——大头不是检索 JS。
  对照实验把话说死了：**空库开面板 48ms，满库开 100ms**，差的那 50ms 就是「每次开都重建 2,548 行结果表」。
- **键入**：CPU 谱里显式出现 `RegExp: [\s\-_/\\.,·、|]+`——那就是 `normKey` 的第 4 步，
  每轮键入对 2,548 行各跑一遍（`blobOf` 拼接 + `toLowerCase` + NFKC + 两条正则）。
- 三档词扫（分离"扫库"与"渲染"两笔）：零命中词 17~19ms、五组全命中并渲染 102 行 20~21ms、
  中文两词渲染 30 行 36~44ms。**渲染行数与耗时反相关** ⇒ 高亮/v-html 不是瓶颈。

## 三、动了的三刀（都在 GlobalPopups.vue）

**刀一：结果表按数据建、按开合露出（#71 的"allResults 惰性化与缓存"）。**
改前 `allResults` 把 `searchActive` 读进 computed ⇒ **关一次面板就是一次依赖变化**，
于是每次开 ⌘K 都重建整表。拆两层：`resultTable` 只读 `d`（建表逻辑一字未改），
`allResults = searchActive ? resultTable : EMPTY_RESULTS`。关着不读 ⇒ 不建；开着时吃缓存；
只有数据真变过（任何一次写库）才重建。

**刀二：匹配用的派生串建行时算一次。** 行上新增 `bl`（命中字段拼接转小写）、`nb`（bl 的归一化）、
`nt`（标题归一化）、`tl`（标题小写）、`cjk`（标题含汉字否）五份，由 `withMatchFields` 在建行时补齐；
`hitResult` 只做子串比较，`hitRank` 不再现场 `normKey(标题)`。`blobOf` 仍是"命中字段清单"的唯一定义处（R58-B4 两端同构那句注释跟着搬过去）。

**刀三：拼音通道加两道闸门 + 每词派生量按查询词缓存。** 这条是这轮最实在的一条，而且是**判据不变、只砍不可能成立的调用**：
`normedParts(parts)` 按词表缓存 `np=parts.map(normKey)`（改前每行每词各跑一遍 normalize+两条正则），
并给每个词算 `py = /^[a-z]+$/.test(p)`。理由是拼音串只由小写字母组成（full 形态再多加空格），
而 `parts` 来自 `q.toLowerCase()`——**含汉字/数字/全角的词面永远不可能是它的子串**。
改前中文查询也逐行进 `pinyinOf` 的 LRU（命中同样要 `delete`+`set` 各一次 touch）。
再加行上 `cjk` 一道，标题没汉字的卡连 `pinyinOf` 都不必进。
另补一条小账：`groupedResults` 的 AI 合并扫描改判"有 AI 命中才扫"——改前五个组各建一份 Set 再把全表 filter 一遍
（`rank` 是空 Map 也照扫，5 × 2,548 ≈ 1.3 万次比较/轮），而 AI 检索是手动按钮、绝大多数键入里它就是空的。

**判停两档（#71 计划里剩的两件，实测不做，证据留在这里）**
- **「高亮分段渲染（不再一次 150 行 v-html）」**：`MAX_PER_GROUP=30` 早已把渲染量钉死在 5×30；
  实测渲染 102 行的那档（20ms）比渲染 30 行的那档（36ms）**更快**，行数与耗时反相关 ⇒ 动 v-html 换不来毫秒，
  只会把 R109/B1 那批以 `hlTitle` 为证据的断言拖进随迁。**不做。**
- **「防抖自适应」**：120ms 防抖买的是"停手前不算"，是延迟不是 CPU；键入净耗时里根本没有"多次重算"这笔（防抖已经合掉了），
  自适应窗口只会让"停手到出结果"的等待时间变得不可预测。**不做。**

## 四、改后读数与召回对照

**官方尺子（perf.cjs `--scale=large`，两轮同机同构建，报告里的 `build` 字段都自证 3.7.1）**

| 指标 | 改前 | 改后 | 读法 |
|---|---|---|---|
| **M5c 唤起（3 次最小）** | 69.5 ms | **48.9 ms** | ★跨过 #71 的「唤起 <60ms」验收线（-30%） |
| M5c 唤起中位 | 70 ms | 55.8 ms | 同向 |
| M5c 窗口内阻塞 / 最大单任务 | 86 / 86 ms | 100 / 100 ms | ★变差了，见下面"第一次开仍然重付" |
| **M3f 搜索面板窗口长任务** | 205 ms / **3 次** | 100 ms / **1 次** | 改前每次开都阻塞一条 68~86ms；改后只有**第一次**开阻塞一条，之后不再阻塞 |
| M5d 键入净耗时（最小 / 中位） | 11.9 / 16.3 ms | 17.0 / 17.4 ms | ★**不声称提速**（第七节 4）：中位持平，最小值反向，而该档噪声带比差值宽 |
| M5d 命中行数 / 渲染行数 | 801 / 30 | 801 / 30 | 尺子自证：命中与渲染都没变少，"变快"不是靠漏卡换来的 |

"最大单任务 86→100ms"这条要正面说清：它不是新增的成本，而是**同一笔建表成本换了归属**。
改前 2,548 行的表在**每次**开面板时重建（三条长任务 68+86+51）；改后只在**数据变过的第一次**开时建（一条 100ms），
后续开面板的窗口里连一条长任务都没有。所以窗口总阻塞 205→100ms、次数 3→1，而墙钟最小值 69.5→48.9ms。
用户的体感是"第二次以后再开面板不卡了"，代价是"改完数据后第一次开仍然要等一下"。

**同一把探针、两个 dist、同种子（2,548 行）对照**（`/tmp/zy_pa_attr.cjs`，两次跑动用的是同一份脚本与同一组采样开关）

| 连开 5 次墙钟 | 82 / 97 / 97 / 101 / 102 | **64 / 66 / 69 / 82 / 81**（五次样本每一次都更低） |
| 三档键入最小值 | 21.5（零命中）/ 34.1（五组 102 行）/ 26.7（30 行） | 20.3 / 27.9 / 31.9 |
| **16 词召回电池** | — | **逐项一致，差异 0**（命中数、组数、首行标题三项全同） |

电池覆盖的通道：中文子串（`资源条目` 1540、`任务标题` 700、`好奇心问题` 300）、拼音首字母（`zy` 1540）、
全拼（`shendu` 两版都是 0——`pinyinOf.full` 是**逐字加空格**的串，`shendu` 不是它的子串，这条不是我改出来的），
ASCII（`AI` 821、`example` 1232）、标签（`效率` 513）、数字（`1` 1275 且五组齐）、
带分隔符归一化（`db skill` 0、`D B` 2240）、台名（`资源台` 0——池卡走显示名单源后叫「资源卡池」，
策展台名是 `策展台 PERF*`，两版一致）、多词 AND、零命中、`备注12`（customFields 不在命中字段清单里）。
**"两版都是 0" 的那些词同样是证据**：它们证明我没有把"本该命中"的东西判没了，也没把"本来不命中"的东西捞进来。

**内存这一档：量不出来，据实说。** 想用 `performance.memory` + CDP `HeapProfiler.collectGarbage` 分离结果表的驻留量，
读数落在 ±14MB 的抖动里（两次"开之前/开之后"的差值都只有 19~22KB，而"关面板之后"反而比"开之前"低），
**这把尺子在这个量级上不可信，不据它下结论**。结构上可以给的是估算：每行新增 5 份字符串，
合成库 blob ≈ 105 字符 ⇒ 约 260 字符/行 ≈ 0.5KB/行，2,548 行 ≈ **1.3MB 量级**（UTF-16），
且它随 `resultTable` 的缓存活到下一次数据变更——不是"关面板就还回去"。
对照：这个库的 `zy_data_v2` 本体是 1,103KB（perf M6 的载荷读数）。要收这笔，
最省的一刀是砍掉 `bl`（原始小写 blob），因为归一化子串判据是它的**超集**——但那是动召回语义的事，本轮不做，留给单独一轮加电池证明。

## 五、召回一条没变：这是这轮最难自证的部分

动的三刀里有两刀直接碰**命中判据**。这类改动一旦把召回改窄：页面照样打开、typecheck 照样 0、
老断言照样绿、E2E 老用例照样过——正是 R4-Da/R4-Dj 记过的"断言还在、证据已空"。两条腿补：

**① 16 词召回对照电池**（同一探针、同一种子、两个 dist 各跑一遍，逐词比 `命中数 / 组数 / 首行标题`）：
中文子串、拼音首字母、全拼、ASCII、数字、带分隔符、大小写混合、零命中、策展台名、任务/好奇/项目三类型……
逐项一致才算过。（结果见第四节）

**② E2E-37**（e2e.cjs，E2E 36→37 条）：真开面板逐档核。种六张卡各盯一条通道——
中文标题、`知识汇总`（拼音首字母 `zshz`）、`db-skill`（词间空格 ≡ 连字符，走 R117-F6 归一化）、
`第 12 号`（数字词：拼音闸门判 false 的那类，必须靠子串）、`lifecycleArchived` 归档卡（**只许进「另有 N 张」，不许进结果流**）、
软删卡（永不许出现）；再加一档**缓存失效验证**：先在关面板状态下经界面新建一张卡（走池控制行「新建」真点击），
再开面板搜它——搜不到就说明结果表缓存把新卡吞了。**归档计数与默认结果集共用同一个 `hitResult`**，
所以这两件事同时也在证明"闸门没改窄召回"。

踩到的一条测试自身的错，记下来免得重演：拼音词面我最初凭读感写成 `zhhz`，跑出来 false。
按 `pinyinTable` 的 `INITIALS` 逐字取，「知识汇总」是 **zshz**（知 z / 识 s / 汇 h / 总 z）。
**这类词面一律按表算，不猜。** 错的是测试的期望值，不是被测代码——但如果不跑这一遍，我会以为是被测代码坏了。

E2E-37 实测（最终构建，37/0 里的一条）：
`全量=4（归档提示「📦 另有 1 张已归档卡片匹配」）拼音 zshz=true 归一「db skill」=true 数字「12 号」=true AND=1 零命中=0 ｜ 缓存失效：建前搜不到=true 建后搜到=1`

   perf 的 M5c/M5d 官方读数也是。发现契机是回归断言里的 `normedParts` 在 src 中零命中——
   **如果我只信标签不信文件，这轮的结论会 whole-sale 错位。**
   改正：每次换文件必当场 `grep -c` 关键符号自证（现在写在命令里），双 dist 对照一律用 `--dist=` 显式指路径，
   不靠"我以为 dist 是哪个"。这条与 R155 那条"报告必须自证测的是哪个构建"同源，这次是我在源头复现了它。
2. **`page.goto` 只改 hash 不会重新加载文档。** 第一次归因跑我 seed 完再 goto 同一个 URL，
   结果测的是启动时那份空库（命中 0、连开 48ms 不衰减），而 perf.cjs:764 早就把这句话写在注释里。
   症状伪装得极好：**面板能开、有行、就是搜不到**——探针差点把"空库 48ms"当成改后收益报出去。
3. **顶栏按钮是 toggle，不是"打开"。** 探针在"已开着"的状态下点它 ⇒ 关掉 ⇒ 后面在关闭的面板上打字
   ⇒ `searchActive=false` ⇒ `allResults` 短路成空表 ⇒ 命中 0、JS 采样几乎为零。
   修法是先看 `.gp-overlay.open` 再决定点不点。**"静默量空"的形状每次都一样：数字很干净，结论全错。**
4. **键入档本机噪声带比收益宽。** 同一个 dist、同一条查询重跑，`资源条目 1` 的净耗时在 29.7~41.2ms 之间摆，
   散布能到 1.4×。所以：**这轮不声称键入提速**，只声称"每轮键入少算了 2,548 次归一化和一批不可能成立的拼音调用"
   （这是结构可数，CPU 谱里那条 normKey 正则从账单上消失是它的直接证据），以及"命中/渲染行数不变、无回退"。
   真要压这一档，下一个杠杆是面板重绘本身（`backdrop-filter: blur(20px)` 挂在整屏遮罩上），不是匹配算式。
5. **`count(p, str)` 的 p 是路径不是内容串。** 我在断言里当内容串用，当场 `ENAMETOOLONG: name too long, open '<一大段源码>'`。
   这条红是断言自己写错，不是被测改动——和 R4-Ea 那条"探针 .bak 被白名单当场抓住"同类，记下来免得下次误读成回归。

## 八、边界如实

- **唤起仍然没有到"零阻塞"**：M5c 的窗口内阻塞仍是 100ms 量级的单条长任务，大头在遮罩层的 `backdrop-filter` 与
  `focus()`（CPU 谱里 `focus` 一项就占 20 个样本）。这属视觉/合成成本，不属检索链路，本轮没碰——要碰是设计决策（模糊强度、遮罩范围），需要用户拍板。
- **面板仍然没有视觉门禁**：本轮补的是 **e2e** 的运行时覆盖，theme-audit 里 ⌘K 面板依旧零场景。
  纯样式改动（比如上面那条 blur）现在仍然没有像素门禁兜着。
- **M5/R7 的浮层指标一字未动**，两轮数字可比（M5a 27ms、M5b 24.2ms、M3b 62→117ms 这一档是 2 次长任务 vs 1 次，与本轮改动无关的采样窗口抖动，未据它下任何结论）。
- **没有做索引/倒排**。零命中词仍然要扫满表（实测 17ms 是 2,548 行的线性扫描地板）。真要做是"给字段建倒排 + 分词表"这件量级的事，且它会把内存从"派生字符串"换成"索引结构"，不是本轮的收尾能顺手带的。
- **键入收益不声称**（见第七节 4）；本轮可归因的实测收益只有唤起一档。
- ZIP 未重打包、未 push。
