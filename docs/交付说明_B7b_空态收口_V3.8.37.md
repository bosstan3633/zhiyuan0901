## 二、四项逐条

### C5 · 方向台空态引导（P2）

**规范要求**：EmptyState（Icon compass）+「从一句愿景开始」+「写下你的方向，逐层拆成可推进的项目」+ 主行动「写下愿景」。

**改前**：`icon="target"` ·「还没有战略目标」· hint 写「点上方『＋ 战略目标』…」· **无主行动**。

**改后**：`icon="compass"` ·「方向台还空着」· desc + hint + **主行动「＋ 写下第一个战略目标」**。

两处调整的理由：

**① 图标 target → compass。** `target`（靶心）说的是「差一个目标数」，带考核味；
`compass`（罗盘）说的是「还没有方向」，是处境。空态的第一眼该说处境。

**② 用词从「愿景」改为「战略目标」。** 产品六层结构是
**愿景 → 使命 → 战略目标 → 项目 → 成功指标 → 任务**，愿景是最顶上那一层，
方向台这一步引导的是战略目标层。规范原文的「从一句愿景开始」用词不准，按母版口径改写。
（`hint` 里仍保留「想先写愿景与使命也行」——那是给想先写上层的人留的路径，不是给本层改名。）

**③ 与 V3.8.27「空态只指路」的裁定冲突，本批做了明确取舍。**
V3.8.27 判过「不给主行动」，理由是 R3-B′ 明确「目标级入口上收页头」，层内再放一个
「＋战略目标」等于开第二入口。**这条顾虑在非空态成立，在零方向时不成立**：
页头那个按钮挂在骨架条第 3 层，零方向时骨架条本身没有内容要铺，
用户首屏视线落在项目塔的空态区，那个按钮既不在视野内、也因为骨架空而无参照——
等于「有入口但够不到」。

解法不是复制按钮，而是**主行动直接调同一个 `addDirection()`**：
同一个函数、同一 toast、同一落地位置，不存在两份实现，也就不会写歪。
非空态下空态不渲染，R3-B′ 的顾虑照旧成立。两条纪律互不覆盖。

### P3 · 项目详情：零任务空态 + 指标口径（P2）

**规范要求**两条：①「空任务 = EmptyState + 在这里把项目拆成可推进的任务」；②「指标一律附口径 tooltip（含对账口径）」。

**① 补项目级零任务空态。** 改前项目详情有三处空态（零项目 / 零指标 / 零附件），
**没有「零任务」这一格**——项目建好、指标定了，就是空着。

放在**项目级**而非每个指标下，理由是任务挂在指标下：
若按「每个指标零任务」各插一个 `EmptyState`，一个刚建的项目会一屏排出 3–5 个图标块
（每个 44px 高），画布直接变成图标墙。项目级只需判一次：
**有指标、但整个项目一条任务都没有**——这才是「项目还只是张骨架」的处境。

主行动两态：有空指标时直接对第一个空指标开新建任务框（一步到位，因为任务必须挂指标才有意义）；
没有空指标时（理论不该发生，判据兜底）退回加指标。

**② 指标读数补口径 tooltip。** `mh-meta` 的「60% · 2/5 任务」原来只有数字。
现在悬停能看到：这个 60% 是多少条已完成除以本指标下多少条任务，
软删的算不算、归属怎么定。口径与 `metricPct` 同源，不另写一套算法。

### W4 · 策展台空态引导（P2）

**规范要求**：空态 = Icon(compass) +「从好奇与资源里搭出你的主线」+ 主行动「添加第一张卡」，呼应「策展成果」定位。

**改前三处**用 `folder` 图标与通用兜底文案，其中**金字塔两处连主行动都没有**。

**改后**：

| 空态 | 改前 | 改后 |
|---|---|---|
| 列表零资源卡 | folder ·「这台还没有资源卡」 | compass ·「这台策展台还空着」· 主行动「＋ 添加第一张卡」 |
| 零节点（有中心论点） | hexagon ·「还没有论点节点」· 无主行动 | hexagon ·「中心论点下面还没有分支」· 主行动「＋ 新建论据分支」+ 幽灵「新建一张论证卡」 |
| 空金字塔（无中心论点） | folder ·「金字塔还空着」· 无主行动 | compass ·「金字塔还空着」· 主行动「＋ 写下中心论点」+ 幽灵「新建一张论证卡」 |

两处主行动**刻意不同**：
- 空金字塔用 `openThesisCreate` —— 建出来的卡自动成为中心论点（L1 根），一步到位；
- 有中心论点时用 `openCreateCat` —— 建子分类作论据分支。

不是笼统的「新建分类」，因为用户此刻缺的是结构里明确的那一层，点了立刻知道自己多了什么。

### D3 · 回收站空态（P2）

**规范要求**：Icon(trash) +「回收站空空如也」+「删除的任务、好奇与资源可在 30 天内找回」+ 无主行动（或「回到调度台」幽灵按钮）。

**改前**：五处**逐字相同**——「这一类还没有删除项」/「删除的卡片会先来这里……」。
用户切到资源卡、分类、任务卡，看到的文案一模一样，等于没有分区。

**改后**：五处按 `tabMeta` 的五个分区别写文案（「这台删除过的资源卡会停在这里」…），
统一补「回到调度台」幽灵按钮，**主行动位留空**。

## 三、★★ 本批最值得记的一条：否决了规范里的「30 天」

规范 D3 原文写「删除的任务、好奇与资源**可在 30 天内找回**」。
本批**没有照抄**，因为**产品里没有这个机制**。

核过的证据（三条独立路径）：

1. **源码**：软删只写 `deletedAt`，全库 grep 不到任何 `purge` / `expire` / `cleanup` / `retention` 定时或过期逻辑，也没有任何地方按天数清理。
2. **母版**：`文档中心/00_产品事实与表达母版.md` 里「30 天」出现 **0 次**。
3. **反向确认**：清空回收站的确认弹层写的是「**不可恢复**」，永久删除按钮也是「不可恢复」——
   全库不存在第二条「会过期」的路径。

**真实口径是软删永久保留**，只有用户主动点「永久删除」或「清空回收站」才真正不可逆。

照抄 30 天的危害是具体的：用户会以为第 31 天卡就没了，
**反而不敢把重要内容放进回收站**——一个空态文案能把软删这个安全网变成心理负担。

已改成「没有期限——软删不会自己过期。只有你点「永久删除」或清空回收站，卡才真正离开本机。」，
并把这条钉成**负锚**（`D3-2`：回收站任何可见文案都不得再出现「30 天 / 月内 / 自动清除」这类未实现的期限承诺）。

> **由此抽出一条通用纪律：照抄规范里的产品承诺前必须先回源码核机制。**
> UI 规范是需求文档，写的时候作者未必核过实现；文案一旦落地就成了对用户的正式承诺。
> 同类还有 C5 的「愿景」（术语错位，见上）。
