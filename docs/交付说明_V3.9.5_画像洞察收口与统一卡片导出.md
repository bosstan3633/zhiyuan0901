### 2.1 「知源卡片」为什么值得单做一层

知源的核心概念是**卡**——三类卡（任务 / 好奇 / 资源）构成全部数据的基础。**既然产品的一切都是卡，那么所有呈现形式与下载方式也该是卡片**，便于阅读、便于传播。此前各导出点各写一套版式，是「同一个产品」这条承诺没落到导出这一层。

契约（唯一模板，新增导出只填内容不画版式）：

1. 顶部眉标（知源 · 卡型）+ 主标题 + 副题（时间范围 / 口径）
2. 读数区：2–4 枚主读数（大字 + 标签 + 口径注）
3. 三类卡带：任务 / 好奇 / 资源 的存量或增量
4. 明细区：0–N 行（时间 + 标签 + 标题），战报 / 热力图 / 月度共用
5. 品牌页脚：知源调度台 · 数据只在本机 · 生成时间

**两条硬约束**（沿用 R172-T12 口径）：

- PNG 走 **canvas 自绘**——不引 `html2canvas`（体积预算已贴顶，且 `foreignObject` 会整片丢外部样式表的色）。
- 颜色一律**现取 `getComputedStyle` 令牌** ⇒ 四主题导出的图与屏上所见一致。

## 三、顺带修掉的真缺陷

### 3.1 theme-audit 的场景间状态依赖

**症状**：`dz-heatmap` 场景「格=0（应 ≥360）」，四主题各少一张图。

**病根**：`dz-day`（日详情）场景会把周期区切到「今天」且**不复位**；`dz-heatmap` 场景接着跑时，`.pi-hmbox` 根本不挂载 ⇒ 实拍的是空屏。

**为什么门禁没拦住**：这不是产品缺陷，是**审计脚本自身的场景顺序依赖**——同类缺陷此前已出现过两次（census 取「最新日期目录」实测读到两周前那份 ⇒「零死样式」是看着绿其实没查）。

**修法**：`dz-heatmap` 场景**显式切回「本年」**再拍。这不是放宽判据，是把场景间的隐式状态依赖显式化。

### 3.2 空库备份让 44 个实拍判据集体失去前置

见 §六「实拍补跑」一节——这是本次盘点中发现的**判据工具缺陷**（`pickData()` 取「按文件名排序的最后一份」，恰是 2026-10-20 那份**空库**），不是产品缺陷。修法与读数见 §六。

## 六、四主题走查（V3.9.4 / V3.9.5 合并补跑，2026-10-21）

机器部分：`theme-contrast.cjs` 全绿。

### 6.1 补跑的原因与过程

**2026-10-21 首次补跑失败**（88 图 ≠ 应有 100，44 个 ✗）：

> `theme-audit.cjs` 的 `pickData()` 取「Downloads 下按文件名排序的**最后一份** `zhiyuan_backup_*.json`」= `zhiyuan_backup_2026-10-20.json`。
> 实测那份是**空库**：资源 0 / 任务 0 / 好奇 0 / 分类 0，仅 1 个空工作台。
> ⇒ 11 个需要数据前置的场景（3 张卡详情 / 池列表 / deck 三件事 / 热力图 / 日详情 / ⌘K 检索 / AI 评审弹窗）**全部拿到空态**。
> 其中 2 个 AI 评审弹窗场景**连弹窗都开不出来**（没有卡可评审）⇒ 图数直接少 12 张。

**这与项目此前记录过的两起同族事故完全一致**：

1. census 取「最新日期目录」的快照，实测读到**两周前**那份 ⇒「零死样式」是**看着绿、其实没查**。
2. `theme-audit` 的方向树折叠判据长期红，真因是备份夹具 `directions[].projects` 全空。

⇒ **判据工具的「自动选数据源」比「手工指定」更危险**：它每次都绿，但绿的是上一次的数据。

### 6.2 修法

`pickData()` 改为**按内容挑而非按文件名挑**：遍历所有候选备份，选**数据量最大**的那份（资源 + 任务 + 好奇 + 分类 + 论证卡合计），而不是「最后一个文件」。理由与 census 同源：**文件名顺序表达的是时间，数据量表达的是前置是否成立**。
