## 0. 一句话结论

本轮不是八个孤立修补，而是四条主线：

1. **卡片池交互去重与去歧义**：好奇心详情只允许一个宿主响应；任务/选题/好奇心三池的“折叠/展开”统一为左侧常驻窄轨；退役顶部“进入卡片池”重复入口。
2. **任务池从“能看”升级为“能快速找问题”**：快捷筛选收进下拉，控制栏重排；按项目分组后，每个项目组可独立折叠；只保留用户确认的“未挂项目 / 未落图 / 未归档 / 主攻项目”语义。
3. **任务状态与选题状态同源同权**：名称、颜色、顺序、增删、完成态全部可自定义，并随云同步；旧 `todo/doing/done` 作为兼容语义层保留，避免历史数据与旧入口失效。
4. **安排历程升级为详情页主模块**：任务与选题详情都把“安排历程”提到首屏主信息区；“设为今日重点”降为次级文字动作。资源卡“全部资源卡”抽屉去掉重复的常用夹入口，系统夹与自建常用夹形成清晰层级。

另有一项独立布局能力：策展台顶部“中心论点”和“全局功能”支持左右拖拽调宽，比例本地记忆、自适应窄屏。

## 2. 功能清单

### F1 · 好奇心详情单宿主，消除重复抽屉

**目标**：任意入口点击一张好奇心卡，只出现一个右侧详情抽屉。

**规则**

1. `CuriosityPanel` 增加宿主标识：`home` / `settings` / `deck`。
2. 只有当前路由对应的宿主可以消费 `onOpenDrawer({ kind: 'curio' })`。
   - 调度台首页：`route.name === 'home'` 且 `details-host="home"`（`/compass` 是方向台，`name` 才是 `compass`）；
   - 设置页：`route.name === 'settings'` 且 `details-host="settings"`；
   - 旧二级池：`/deck/curiosity` 且 `secondary-mode`。
3. 非当前宿主只保留列表/高亮职责，不打开详情。
4. `KeepAlive` 缓存命中时不改变上述判定；`onActivated/onDeactivated` 只作为辅助，不作为唯一依据。
5. 抽屉关闭事件仍按现有 `emitDrawerClosed` 广播，设置页附件刷新不受影响。

**验收**

- 未访问设置页：点击好奇心卡 → 1 个 `.drawer`。
- 先访问设置页再回调度台：点击 → 仍只有 1 个抽屉。
- 先访问 `/deck/curiosity` 再回调度台：点击 → 仍只有 1 个抽屉。
- 设置页内点击好奇心卡：只有设置页宿主打开 1 个抽屉。

### F2 · 三卡池左侧折叠/展开统一

**目标**：折叠入口与展开入口永远在左侧同一位置，符合“左侧栏”操作心智。

**统一形态**

- 展开态：左栏宽 `220–310px`，栏头左侧显示「‹ 折叠」。
- 折叠态：左栏收缩为 `44px` 常驻窄轨，窄轨顶部显示「›」+ 竖排/短标签（任务清单 / 选题清单 / 好奇心清单）。
- 展开按钮不再出现在右侧日历头或顶部工具栏。
- 键盘：按钮可 Tab 聚焦，Enter/Space 切换；`aria-expanded` 正确。
- 窄屏（≤900px）：仍保留左侧窄轨；若布局改为上下堆叠，窄轨变为顶部 44px 横条，不回到右侧。

**覆盖**

| 池 | 组件 | 现状 | 目标 |
|---|---|---|---|
| 任务卡 | `TaskCalendarView.vue` | 折叠左、展开右 | 左侧常驻窄轨 |
| 选题卡 | `TopicManagerPanel.vue` | 展开在工具栏右 | 左侧常驻窄轨 |
| 好奇心卡 | `CuriosityWorkbench.vue` | 展开在工具栏右 | 左侧常驻窄轨 |

**验收**

- 三池折叠后，展开按钮的屏幕横坐标均小于右栏起点。
- 折叠/展开不改变当前筛选、排序、视图模式与滚动位置。
- 折叠状态下右栏宽度自适应，不出现横向滚动条。

### F3 · 退役“进入卡片池”入口

**目标**：一级卡片池就是唯一工作台，不再提供“再进一层”的重复入口。

**规则**

1. 删除卡片池页头右侧「进入卡片池 →」。
2. 保留 `/deck/task|topic|curiosity|resource` 路由与重定向，老书签不 404。
3. 资源页签内原「查看全部 / 全部」若仍存在，改为直接打开「全部资源卡」右侧抽屉，不再调用 `goDeck`。
4. `goDeck()` 若无任何 UI 消费方则删除；如保留兼容函数，不得再出现在模板按钮上。
5. 更新回归断言：原来锁定 `@click="goDeck(handTab)"` 的用例改为锁定“入口不存在 + 抽屉直达”。

**验收**

- 卡片池页头无“进入卡片池”文案与按钮。
- 点击资源页“查看全部”直接打开全部资源卡抽屉。
- `/deck/task` 等旧地址仍可打开或被重定向到一级池对应页签。

### F4 · 任务控制栏重排 + 项目分组可折叠

**目标**：一屏内快速回答“哪些任务没挂项目、哪些没落图、哪些还没归档”，并能在按项目分组时逐组收放。

#### F4-1 控制栏

**结构**

```text
[搜索任务、项目或指标............] [项目 ▾] [状态 ▾] [快速筛选 ▾]
[排序 ▾] [分组 ▾] [月历|看板] [月历显示已完成] [清空筛选]
```

- 第一行主筛选：搜索框弹性占满，三个下拉等宽，不允许挤压成图标。
- 第二行视图与次要筛选：排序、分组、视图切换、显示已完成、清空。
- 每个下拉有可见标签或 `aria-label`；移动端自动换行，不横向溢出。
- “快速筛选”下拉选项带计数：
  - 全部（N）
  - 未挂项目（N）
  - 未落图（N）
  - 未归档（N）
  - 主攻项目（N）
- 不再使用五个并排快捷按钮。

#### F4-2 项目分组折叠

- `groupMode === 'project'` 时，左侧列表按项目分组。
- 每个组头可点击折叠/展开，显示项目名、任务数、折叠箭头。
- 组头是按钮，支持键盘；`aria-expanded` 正确。
- 栏头提供「全部折叠 / 全部展开」轻量动作。
- 折叠仅影响该组任务，不影响右侧月历/看板。
- 默认全部展开；切换筛选后保留仍存在的组的折叠状态。
- “未挂项目”作为固定组，同样可折叠。

**验收**

- 五个快捷按钮零残留。
- 选择“按项目分组”后，组头可逐组收放；折叠后计数仍显示。
- 任务筛选与分组组合正确，不出现跨组重复卡片。

### F5 · 资源卡：全部资源抽屉与系统夹层级

**目标**：一级资源页只保留“系统夹 + 自建常用夹”两层；全部资源抽屉不再重复常用夹入口。

#### F5-1 全部资源卡抽屉

- `PoolCardsPanel` 增加 `hide-folder-entry` 开关；在「全部资源卡」抽屉中为 `true`。
- 抽屉内移除顶部「常用夹 N」按钮。
- 保留：搜索、筛选、网格/列表、批量选择、批量打标签、批量删除、镜像、右键菜单、AI 入口、新建/导入。
- 单卡上的“加入常用夹”动作保留，因为它是卡片级操作，不与顶部入口重复。

#### F5-2 系统夹与自建夹分层

- 「全部资源卡」「今日采集」进入独立“系统夹”区：
  - 高度从 92px 降到约 64–70px；
  - 使用强调底色/左侧色条/更明确的图标，仍比自建夹更醒目；
  - 一行两枚，保持并列。
- 自建常用夹进入“我的常用夹”区：
  - 普通尺寸卡片；
  - 与系统夹之间有分隔标题或间距；
  - “管理 / 新建常用夹”入口保留在自建区。
- 没有自建夹时，系统夹仍完整显示，空态提示不抢占系统夹位置。

**验收**

- 全部资源抽屉内无「常用夹」顶部按钮。
- 系统夹视觉尺寸小于自建夹但识别度更高。
- 批量、镜像、右键能力无回归。

### F6 · 策展台顶部双栏可拖拽

**目标**：中心论点与全局功能的宽度由用户决定，二者自适应填满容器。

**规则**

- 两栏之间新增 10–12px 拖拽分隔条，hover/focus 有明确反馈。
- 拖拽范围：左栏最小 320px、右栏最小 340px；整体比例限制在 32%–72%。
- 双击分隔条恢复默认比例（约 62% : 38%）。
- 键盘：分隔条 `role="separator"`，`aria-orientation="vertical"`，左右方向键每次调整 2%，Home/End 跳到边界。
- 比例写入 `UIPrefs.wsConsoleSplit`，本地记忆，不进入业务云同步。
- ≤900px 时取消双栏拖拽，回到上下堆叠；分隔条隐藏。
- 四套主题下分隔条与 focus ring 使用现有 token，不新增硬编码颜色。

**验收**

- 拖拽时两栏实时变化，无内容溢出。
- 刷新后比例保留；双击复位。
- 键盘可完整操作，焦点可见。

### F7 · 任务状态自定义（对齐选题卡）

**目标**：任务状态从固定三值升级为业务数据；用户可改名、改色、排序、增删，并指定唯一完成态。

#### F7-1 数据契约

```ts
type TaskStatusBucket = 'todo' | 'doing' | 'done'

interface TaskStatusDef {
  id: string
  name: string
  color: string
  order: number
  bucket: TaskStatusBucket
  terminal?: boolean
}

interface TaskCard {
  statusId?: string   // 新真源
  status: 'todo' | 'doing' | 'done' // 兼容层，始终等于 statusId 的 bucket
}
```

- 默认三档：待开始（todo）/ 进行中（doing）/ 已完成（done，terminal）。
- 有且只有一个 `terminal`，且必须属于 `done` 桶。
- 新增自定义状态必须选择语义桶；非完成桶可任意增加。
- 删除状态时，受影响任务迁移到同桶或第一个非完成状态；至少保留一个状态。
- 旧数据无 `statusId`：按 `status` 自动落到同桶默认状态。
- 云恢复、导入、三方合并后统一归一化，修复悬空 `statusId`、多完成态、缺失状态列表。

#### F7-2 设置入口

- 设置 → 任务卡 → “任务状态”编辑器，交互与选题状态一致：
  - 行内改名、改色；
  - 上移/下移；
  - 新增（名称 + 颜色 + 语义桶）；
  - 删除（带影响任务数确认）；
  - 设为完成态。
- 说明文案明确“看板列、详情徽标、任务筛选共用这一套状态，并随云同步”。

#### F7-3 消费面

- 任务详情：状态 chip 显示自定义名称与颜色；菜单列出全部状态。
- 任务看板：列由状态定义动态生成，支持拖动改状态。
- 任务月历：左侧状态标签、状态点、日历 chip 颜色使用自定义颜色。
- 任务池筛选：状态下拉由状态定义生成。
- 今日三件事 / 项目树 / 项目全景：至少按语义桶正确显示“完成/未完成”，不因自定义状态误判。
- 旧 `TaskManagerPanel`（`/deck/task` 兼容页）：允许继续按三桶显示，但不得因自定义状态丢卡。

**验收**

- 改名/改色后，任务详情、看板、月历、筛选同步变化。
- 新增“等待中（doing 桶）”后，看板出现新列，旧任务不受影响。
- 取消完成/恢复完成语义仍正确。
- 云同步、导入导出、旧备份恢复后状态引用有效。

### F8 · 任务/选题详情：安排历程主模块

**目标**：让用户一眼看到“这张卡被安排过几次、每次从哪天改到哪天、何时改的”，并可直接删减某个时间点。

#### F8-1 安排历程视觉

- 独立主模块，位于标题/状态之后、项目归属之前。
- 头部：
  - 标题「安排历程」+ 次数；
  - 当前计划 chip：「当前计划：11/20 周四」或「未落图」；
  - 最近一次安排时间。
- 时间轴：
  - 纵向时间线 + 节点；
  - 每条显示“从 X 改到 Y”或“安排到 Y”；
  - 显示操作时间与来源（详情设置 / 日历拖拽 / 今日重点 / 快捷菜单 / AI 采纳 / 导入）；
  - 最新一条有强调态；
  - 每条有删除按钮，删除后 Toast 可撤销。
- 超过 5 条时“显示全部 / 收起”。
- 空态：说明从本版本开始记录，并显示当前计划。
- 删除的是“历程事件”，不改当前 `dueDate`；文案必须写清。

#### F8-2 任务详情

- 顺序：标题/状态 → 安排历程主模块 → 项目/指标 → 资源镜像 → 说明 → 链接/标签。
- 日期输入收进主模块的“当前计划”行，不再单独占一块。
- 「设为今日重点」从整块主按钮降为模块右上角次级文字按钮/图标按钮，tooltip 说明会写入今天计划。
- 保留“无截止日期字段、留空即未落图”的说明，但缩短为一行提示。

#### F8-3 选题详情

- 与任务同构：计划日期 + 状态 + 安排历程组成主模块。
- 「设为今日重点」同样降为次级动作。
- 状态选择保留在模块内，但视觉弱于历程。

**验收**

- 任务/选题详情首屏可见安排历程，无需滚动到页面中部。
- 连续四天安排同一张卡，时间轴出现四条，日期链正确。
- 删除某条后当前计划不变；撤销可恢复。
- “设为今日重点”不再抢主视觉。

## 3. 非目标与边界

1. 不恢复“已逾期”概念；任务仍只有“计划执行日期”。
2. 不重做四卡池信息架构；只在现有结构上收口交互。
3. 不把 `/deck/*` 物理删除；只退役入口，保留兼容路由。
4. 不新增第二套计划日期字段；继续使用 `TaskCard.dueDate` / `TopicCard.dueDate`。
5. 不把任务状态做成纯 UI 偏好；它必须进入业务数据、导入导出与云同步。
6. 不在本轮引入看板按项目泳道；项目分组只作用于左侧列表。
7. 不改安排历程已有事件协议 `PlanScheduleEvent`，只改展示与操作层。
