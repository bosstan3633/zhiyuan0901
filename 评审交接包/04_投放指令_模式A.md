## §8 · 纠偏话术（模型跑偏时直接复制）

| 症状 | 粘贴这句 |
|---|---|
| 说空话（"建议加缓存""提升可维护性"） | `你这条建议我看不出它解决了什么可观测的问题。请用「现象 → 证据 → 影响」重写。` |
| 行号对不上 / 编造路径 | `你引用的行号我在仓库里对不上。请重新读那个文件，并把真实行号贴出来。对不上就标「推测」。` |
| 给通用最佳实践 | `这是通用建议，不是针对本项目的。请说明它在本项目的哪个具体位置成立、不成立会怎样。` |
| 重复已否决方向 | `这条方向在 01_项目透视卡 §3.1 的 ADR 表里已被明确否决。除非你能说明当时的取舍理由现在为何不成立，否则请撤回。` |
| 把推测当事实 | `这条是推测。请标注「推测」，并给出验证方法（命令或代码位置）。` |
| 越读越多、开始读整个仓库 | `停。不要再扩大阅读范围。请基于已读内容先给出当前结论，并说明还缺什么信息。` |
| 建议很美但拆红线 | `这条会破坏红线 X。请说明：如果不破这条红线，有没有替代方案？如果必须破，代价是什么？` |

## §9 · 拿到输出后的验收清单

- [ ] **复述有没有事实错误** —— 有则整体可信度打折，让它重读 `01` 再继续
- [ ] **证据里的行号能否在仓库里对上** —— 本项目的文档行号经常过期，这条必须抽检 3~5 条
- [ ] **有没有"看起来很美但会拆掉红线"的建议** —— 这类最危险：方案本身可能确实更好，但代价是项目赖以成立的约束
- [ ] **「三件事」有没有给出取舍理由** —— 若只是把前三名照抄一遍，说明它没有真正排序
- [ ] **有没有出现 ADR 表里已否决的方向** —— 出现即说明它没认真读 §3.1

> 最后一条尤其重要：本项目的多条红线（卡间零挂载 / 软删 / 本地优先 / AI 不代决策）**不是技术偏好，而是产品承诺的实现方式**。
> 一条建议如果让"删除可恢复"或"数据不出本机"不再成立，无论技术多优雅，都应直接否决。

## §10 · 两种推进方式

**方式一：同一会话连续推进（推荐）**
按 §1 → §2 → §3+§4 → §3+§5 → §3+§6 → §7 顺序发，模型保留前文记忆，收敛质量最好。
风险：上下文会被读入的代码逐步占满。**若模型开始"忘记"前面的约束，就是上下文不够了** —— 改用方式二。

**方式二：每轮新开会话（上下文紧张时）**
每轮新会话，按此模板拼装：

```
[§1 开场指令]
[§2 或 §4/§5/§6/§7 的本轮指令]
[§3 红线速查卡]
[上一轮结论摘要：把 R1/R2/R3 的输出原文粘进来]
```

代价是每轮都要重新建立心智模型（多花约 1.5 万 token），换来的是每轮上下文都是干净的。
