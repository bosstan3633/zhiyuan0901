# 评审交接包 · 使用说明与执行策略

> 目的：把「知源调度台」这个项目，用**尽量少的 token** 交给一个**最先进的模型**，让它给出**产品架构 / 性能 / 产品**三个维度的有效建议。

---

## 一、为什么需要这个包（问题的本质）

直接投喂是行不通的：

| 方式 | 体量 | 问题 |
|---|---|---|
| 全量投喂代码 | 178 文件 / **42,658 行** ≈ **47 万 token** | 超出多数模型单次上下文；即便塞得下，信噪比极低 |
| 全量投喂文档 | `docs/` 408 份（交付说明 185 + 需求盘点 69）+ `文档中心/` 115 份 | 其中 90% 是历史轮次的交付流水，对"如何改进"零贡献 |
| 只给 README | 几百行 | 模型看不到真实的债务、红线与性能矛盾，只能给通用建议 |

**本包的做法**：不投喂"内容"，投喂**结构 + 事实 + 索引**。

- 模型**先**拿到「这是什么 / 怎么组织的 / 数字是什么 / 过去做过什么决策」（约 1.2 万 token）
- **然后**由模型自己决定"为了回答这个问题，我还需要看哪几个文件"
- 需要时**点名索取**具体文件（每个文件按需注入，几百到几千 token）

> **压缩比（2026-10-04 实测）**：真正**投喂给模型**的是 `01`+`02`+`03`，合计 **719 行 / 75,108 B / ≈1.7 万 token**，
> 对比全量投喂代码的约 **47 万 token**（42,658 行 / 2,104,129 字符）——**≈ 28:1**。
> （`00` 与 `04` 是给你这个"人类编排者"看的**操作说明**，**不投给模型**；全包五个文件共 1,206 行 / 100,461 B / ≈2.2 万 token。）
> 口径：token 按 4.47 字符估算（与 09-23 版同一把尺子），比值随 `01` 增删而变——**别把它当精确数**。
> 且信息密度更高：留下来的全是"会影响判断"的东西，剔掉的是"历史流水"。
>
> ⚠ 上面用的是**取整值**，因为任何一处文字修改都会让精确值过期（本包在定稿过程中就变了三次）。
> 需要精确值时按 §七 的命令重算，**不要信任文档里手写的精确数字**。

| 文件 | 内容 | 层级 | 体量 |
|---|---|---|---|
| `00_使用说明与执行策略.md` | 本文件：怎么用、怎么问、怎么防跑偏 | — | 约 200 行 |
| `01_项目透视卡.md` | 一页纸 + 架构骨架 + 实测证据 + 决策史与争议点 + **与 09-23 版的差异账** | **L0–L3** | 约 260 行（核心） |
| `02_代码索引.md` | 178 个文件逐个标注：行数 / 职责 / 导出符号 + 债务候选 + 脚本清单 | **L4** | 316 行 |
| `03_评审结果模板.md` | 要求模型按此结构输出（保证建议可比、可落地） | — | 119 行 |

**投放方式**：模式 A 直接用 `04`；模式 B / C 用本文件 §三 的对应说明 + §五 的 Prompt 模板。

## 三、三种投放模式（按目标模型的能力选）

### 模式 A · 模型能读文件（**最优**，推荐）

适用：Claude Code / Cursor / 带文件工具的 API / 任何能访问仓库的 agent。

**→ 直接用同目录 `04_投放指令_模式A.md`**（已按本模式写好，每个代码块可原样复制，不需要改写）。

要点回顾：

1. 把整个仓库（或至少 `v2/src` + `文档中心/05_研发与数据/`）给模型
2. 投喂 `01` + `02` + `03`
3. 用 `04` 里的 §1 开场 + §2~§7 五轮指令推进

**为什么最优**：模型可以自己 grep / 读文件，**按需取用**，不必一次吃下全部。你只需要给它"地图"（`02`）和"背景"（`01`）。

### 模式 B · 模型只能对话（无文件访问）

适用：网页版对话。

按**维度分批**投喂，每批只给该维度需要的材料：

| 批次 | 投喂内容 | 追问 |
|---|---|---|
| 第 0 批 | `01` 全份 + `02` 的「§一 债务候选」 | "你还需要什么信息？请列清单" |
| 第 1 批（架构） | `02` 全份 + 点名索取 3~5 个关键文件全文 | 架构问题 |
| 第 2 批（性能） | `01 §2.3 / §2.4` + 点名索取热点文件 | 性能问题 |
| 第 3 批（产品） | `01 §L0` + `文档中心/00_产品事实与表达母版.md` | 产品问题 |
| 第 4 批（收敛） | 把前三批结论回灌，要求排序 | 输出方案 |

> ⚠ 模式 B 下**不要**一次把 `02` 里所有文件都要过来。让模型**分轮点名**，每轮只要 3~5 个文件。

### 模式 C · 模型能访问 Git 仓库

适用：给一个 repo 链接 + 有浏览能力的模型。

给 `01` + `03` + 仓库链接，并明确告诉它：
> 仓库根目录的 `评审交接包/02_代码索引.md` 是你的地图；`文档中心/05_研发与数据/` 是架构与数据模型的权威说明。

## 四、推荐执行流程（五轮）

**核心原则：先建模，再诊断，最后收敛。不要一上来就要"改进方案"。**

| 轮次 | 目标 | 输入 | 输出要求 |
|---|---|---|---|
| **R0 心智建模** | 确认模型真的理解了项目 | `01` + `02` | ① 用 200 字复述产品是什么、给谁、不做什么　② 列出"为了给出有效建议，我还需要看哪些文件"（**必须点名，不许泛泛而谈**） |
| **R1 架构诊断** | 产品架构层面的问题 | R0 的点名文件 | 每个问题：现象 → 证据（文件:行号）→ 根因 → 代价 |
| **R2 性能诊断** | 性能瓶颈 | `01 §2.3/2.4` + 热点文件 | 同上；**必须区分"实测"与"推测"** |
| **R3 产品诊断** | 产品体验/信息架构 | `01 §L0` + 母版 + 相关视图 | 同上 |
| **R4 收敛** | 可执行方案 | R1–R3 结论 | 按「影响 × 成本 × 风险」排序，标注会触碰哪条红线 |

> **为什么强制 R0**：本项目最大的历史教训就是"**书面结论与代码实装不一致**"（曾出现文档说"待排期"、代码三年前已交付的坏账）。
> 如果模型不先复述理解、不先点名要文件，它给出的建议大概率是**基于通用经验而非本项目实际**的。

## 五、Prompt 模板（可直接复制）

### 模板 1 · 开场（R0）

```
你是一位资深的产品架构与前端性能评审专家。我将给你一份「项目透视卡」和一份「代码索引」，
这是一个真实在用的 Chrome MV3 扩展项目（接管新标签页），约 4.3 万行 TypeScript/Vue。

请先做三件事，**不要急着给建议**：
1. 用 200 字以内复述：这个产品是什么、给谁用、明确不做什么、技术形态是什么。
2. 指出这份材料里你**无法判断**或**自相矛盾**的地方。
3. 列出为了给出「产品架构优化 / 性能提升 / 产品优化」三类有效建议，
   你还需要查看哪些**具体文件**（请给出文件路径，并说明每个文件你想看什么）。
```

### 模板 2 · 分维度诊断（R1–R3）

```
现在只聚焦【架构 / 性能 / 产品】这一个维度（其余维度本轮不评）。

约束（必须遵守）：
- 每条结论必须给出**证据**：文件路径 + 行号，或 `01_项目透视卡` 里的具体实测数字。
  没有证据的，请明确标注为「推测」。
- 每条建议必须回答：**它解决了什么可观测的问题**（不要"代码更优雅"这类理由）。
- 如果某条建议会破坏以下任一红线，必须显式指出：
  卡间零挂载 / 软删 / 令牌化样式 / 版本号单一来源 / 回归断言只增不减 / AI 密钥只在 zy_ai_v1 且入口 chunk 零 AI 字面量。
- 本项目已明确否决的方向（见透视卡 §3.1 ADR 表），**不要重复建议**；
  除非你能给出「为什么当时的取舍理由现在不成立」。
```

### 模板 3 · 收敛（R4）

```
把前面几轮的结论收敛成一份可执行方案，按以下格式输出（用表格）：

| # | 建议 | 维度 | 影响（解决什么） | 证据 | 成本 | 风险（碰哪条红线） | 优先级 |

排序规则：先「影响大 + 成本低 + 不碰红线」，再「影响大 + 成本高」，最后「影响小」。
最后请单独回答一个问题：
**如果只能做三件事，你选哪三件？为什么？**
```

## 六、反退化机制（**这是本包最重要的部分**）

本项目的核心痛点**不是"没人给建议"，而是"建议脱离了代码的真实状态"**。为此内置四道防线：

| 机制 | 做法 | 防的是什么 |
|---|---|---|
| **证据强制** | 每条结论必须带 `文件:行号` 或实测数字 | 防"通用最佳实践"式空话 |
| **确证/推测分离** | 无证据的必须标「推测」 | 防模型把猜测当事实（本项目最贵的教训） |
| **ADR 免疫** | 已否决方向不得重复建议 | 防"建议做云同步 / 虚拟滚动 / 卡间挂载"这类已被拍板否决的方向 |
| **红线标注** | 建议若触碰红线必须显式声明 | 防"方案很好但会把卡间零挂载这条红线拆掉" |

**另外两条给使用者的提醒**：

1. **不要向模型隐瞒"已知争议点"**（透视卡 §3.4）。把内部没想清楚的问题摊开，模型才可能给出真正的新视角；否则它只会重复你已有的结论。
2. **对模型给的所有"数字"保持怀疑** —— 包括它引用你材料里的数字（可能记错）和它自己推算的数字（多半不准）。**数字一律回仓库复核**。

## 七、维护（怎么保证不过期）

这个包会腐化，但腐化点是**可控且可自动化的**：

| 部分 | 腐化风险 | 维护方式 |
|---|---|---|
| `02_代码索引.md` | **高**（代码天天变） | **自动生成**：`cd v2 && node scripts/gen-code-index.cjs`。改完代码跑一次即可 |
| `01_项目透视卡.md` §L2 数字 | **高** | 每轮发版时更新；或评审前重跑门禁取数（见下） |
| `01_项目透视卡.md` §L0/L1/L3 | 低（架构与决策史变化慢） | 架构变更或新 ADR 时更新 |
| 本包体量（行数 / token） | 中 | **不要手写**；用下方一行命令重算 |

**重算本包体量**（改完任何文件后跑，避免"压缩比"这类数字失真）：

```bash
cd 评审交接包
wc -l *.md                                    # 各文件行数
du -b 01_*.md 02_*.md 03_*.md | awk '{s+=$1} END {print s" B  ← 投喂体量"}'   # 只算投给模型的三个
wc -c 01_*.md 02_*.md 03_*.md | tail -1       # 同上（wc 口径）
```

> **注意口径**：压缩比的分子只能是 **`01`+`02`+`03`**（真正投给模型的部分）。
> 把 `00`/`04` 这两份"给人看的操作说明"算进去会让数字虚高——**口径写错比数字写错更坏**。

**评审前刷新数字的最快路径**：

```bash
cd v2
node scripts/regression.cjs      # 静态回归（2026-10-04 实测 1636/0）
npx vue-tsc --noEmit             # 类型（当前 0 错误）
node scripts/gen-code-index.cjs  # 刷新代码索引
node scripts/pack.cjs            # 刷新体积（ZIP / 单文件 / 入口 chunk）
node scripts/perf.cjs --scale=medium   # 性能（注意：需独占机器，多次取中位；整跑约 1.5 分钟）
node scripts/e2e.cjs           # 运行时（2026-10-04 实测 42/0，真点真写库）
node scripts/theme-audit.cjs   # 视觉走查 104 图 + DOM 类名普查（约 6 分钟）
node scripts/img-diff.cjs --batch <A目录> <B目录>   # 像素 A/B：0 差 / 抖动 / 变化 三档
```

> ⚠ **性能数字有一条铁律**（本项目血泪）：**同机 A/B 交替采样**，禁止跨时间比数字。
> 同一台机器上同一个包的两次读数可以差 24%；M3 长任务四次采样可差近 5 倍。
> 用 `perf.cjs --dist=<包>` 做同机对比，且读报告前先核报告里的 `build` 字段是否等于预期版本。
