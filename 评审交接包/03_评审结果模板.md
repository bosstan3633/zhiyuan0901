# 评审结果模板

> 给评审模型的**输出契约**。要求模型按此结构产出，目的有三个：
> ① 让建议**可比**（同一套字段，不同轮次/不同模型的结果能横向排）；
> ② 让建议**可落地**（强制写清"改哪里、代价是什么、碰不碰红线"）；
> ③ 让空话**无处藏身**（没有证据的条目会被格式本身暴露出来）。

---

## 一、总输出结构

模型应输出四个部分，顺序固定：

```
① 理解复述（200 字内）
② 问题清单（表格，按维度分组）
③ 方案排序（表格，按优先级）
④ 三件事（如果只能做三件）
```

---

## 二、① 理解复述

**要求**：200 字以内，回答四问 —— 是什么 / 给谁 / 不做什么 / 技术形态。
**作用**：这是"模型是否真的读进去了"的**唯一低成本检验**。若复述出现事实错误，后续建议全部作废。

---

## 三、② 问题清单

每个维度一张表，字段固定：

| 字段 | 含义 | 硬性要求 |
|---|---|---|
| **ID** | `A-01` / `P-01` / `U-01`（架构/性能/产品） | 便于跨轮引用 |
| **现象** | 用户或系统能观测到什么 | 写"可观测的事实"，不写"代码不够好" |
| **证据** | `文件:行号` 或实测数字 | **没有证据 → 必须在"确证度"列标「推测」** |
| **确证度** | `实测` / `代码确证` / `推测` | 三选一，不许留空 |
| **根因** | 为什么会这样 | 若不确定，写"待验证"并给出验证方法 |
| **影响面** | 谁受影响、多大范围 | 量化优先（多少文件 / 多少场景 / 多少 ms） |

## 四、③ 方案排序

一条建议一行，字段固定：

| 字段 | 含义 |
|---|---|
| **对应问题** | 引用②里的 ID（**不许出现没有对应问题的建议**——"顺便优化一下"是禁止的） |
| **方案** | 做什么（一句话说清） |
| **改动落点** | 哪些文件 / 哪一层（架构层 / 数据层 / 视图层 / 门禁层） |
| **影响** | 解决什么可观测的问题，**量化优先** |
| **成本** | 工作量级 + 是否需要数据迁移 + 是否触及 E2E 面 |
| **风险 / 红线** | 会碰哪条红线（单向挂载 / 软删 / 令牌化 / 版本号 / 断言只增不减）；无则写「无」 |
| **优先级** | P0 / P1 / P2 |

| # | 对应问题 | 方案 | 改动落点 | 影响 | 成本 | 风险/红线 | 优先级 |
|---|---|---|---|---|---|---|---|
| 1 | | | | | | | |

**排序规则**（要求模型显式遵守）：
1. 先「影响大 + 成本低 + 不碰红线」
2. 再「影响大 + 成本高」
3. 最后「影响小」
> 反直觉但重要：**「影响小 + 成本低」的条目优先级应低于「影响大 + 成本高」**——本项目历史上已经因为沉迷小修小补，让最大的一笔债（性能 M3）拖了 40 轮。

---

## 五、④ 如果只能做三件事

> 如果只能做三件事，你选哪三件？为什么？

**要求**：必须给出**取舍理由**（为什么放弃其他的），而不是重复前三名。
这一问是**检验模型是否真的做了优先级判断**的关键——不回答这一问，或把前三个照抄一遍，说明它没有真正排序。

---

## 六、输出自检清单（模型在提交前应自行核对）

- [ ] 每条问题都有证据，或已明确标注「推测」
- [ ] 每条建议都能对应到一个问题 ID
- [ ] 没有建议已被 ADR 表否决的方向（除非给出了推翻理由）
- [ ] 触碰红线的建议已显式标注
- [ ] 没有出现"代码更优雅""提升可维护性"这类**不可观测**的理由
- [ ] 「三件事」给出了取舍理由
- [ ] 所有引用的数字，都能在 `01_项目透视卡` 或仓库里找到出处

---

## 七、给使用者的验收提示

拿到模型输出后，**优先核三件事**：

1. **复述有没有事实错误** —— 有则整体可信度打折
2. **证据能不能在仓库里对上** —— 尤其行号（本项目文档里的行号经常过期）
3. **有没有"看起来很美但会拆掉红线"的建议** —— 这类最危险，因为方案本身可能确实更好，但代价是项目赖以成立的约束

> 最后一条尤其重要：本项目的多条红线（单向挂载 / 软删 / 本地优先）**不是技术偏好，而是产品承诺的实现方式**。
> 一条建议如果让"删除可恢复"或"数据不出本机"不再成立，无论技术多优雅，都应直接否决。
